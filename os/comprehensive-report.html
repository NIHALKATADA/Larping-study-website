Unit I: Intro to OS

Operating System

An Operating System (OS) is system software that acts as an intermediary between computer hardware and the computer user. It manages hardware resources and provides common services for computer programs, ensuring efficient and convenient execution of user applications.

List any four functions of an Operating System
  • Process Management: Scheduling and execution of processes.
  • Memory Management: Allocation and de-allocation of memory space.
  • File Management: Organizing and tracking files and directories.
  • Device/I/O Management: Managing device drivers and hardware communication.
Mode Bit

The Mode Bit is a hardware flag used by the OS to differentiate between user-level and system-level execution to protect system integrity.

  • 0: Kernel Mode (System/Supervisor mode) - full access to hardware.
  • 1: User Mode - restricted access.
User Mode and Kernel Mode
User Mode (Mode bit = 1)Kernel Mode (Mode bit = 0)
Restricted access to memory and hardware.Direct access to all memory and hardware.
Cannot execute privileged instructions.Can execute any CPU instruction.
Application programs run here.Core OS components run here.
Why is DMA (Direct Memory Access) more efficient than Programmed I/O

In Programmed I/O, the CPU must actively monitor and transfer every byte of data between the device and memory, wasting CPU cycles. DMA is more efficient because a dedicated DMA controller handles the bulk data transfer directly to/from memory, allowing the CPU to perform other tasks concurrently. The CPU is only interrupted once the entire block is transferred.

Hardware Interrupts and Software Interrupts

Hardware Interrupts are asynchronous signals generated by external hardware devices (e.g., keyboard press, disk I/O completion) to get the CPU's attention. Software Interrupts (Traps) are synchronous signals generated by executing instructions within a program (e.g., system calls, division by zero errors).

User program tries to directly access a printer without going through the OS

The hardware will generate a trap (exception), and the OS will terminate the program. This happens because accessing I/O devices requires executing privileged instructions, which are strictly forbidden in User Mode (Mode bit = 1) to ensure system security and prevent hardware conflicts.

While a user is typing a document in MS Word, a timer interrupt occurs in the background

The moment the timer interrupt occurs, the hardware automatically changes the mode bit from 1 (User Mode) to 0 (Kernel Mode). This transfers control to the OS's interrupt handler routine so the OS can safely perform scheduling or background tasks with full hardware privileges.

Student's program gets stuck in an infinite loop

The Timer (Hardware Timer) mechanism prevents permanent freezing. The OS sets a timer to interrupt the CPU after a specific time slice (quantum). When the timer expires, it generates an interrupt that forces the CPU back into Kernel Mode, allowing the OS to regain control and forcefully terminate or preempt the looping program.

Explain, in brief, why a Monolithic OS structure is fast but hard to maintain, whereas a Microkernel structure is more reliable but comparatively slower

A Monolithic OS bundles all services (file system, drivers, memory) into a single large kernel, making execution fast (no message passing overhead) but hard to maintain due to tight coupling. A Microkernel keeps only essential services in the kernel and runs the rest in user space; this is reliable (a failed driver won't crash the OS) but slower due to the overhead of inter-process communication (IPC) and frequent mode switching.

List and briefly explain any three functions of an Operating System
  • Process Management: The OS creates, schedules, and terminates processes, allocating CPU time fairly among them.
  • Memory Management: It tracks which parts of memory are in use, allocating and deallocating RAM to programs as needed to optimize performance.
  • File Management: It provides a logical view of information storage, mapping files onto physical storage devices and managing access permissions.
Batch Operating System and mention one limitation of this type of system

A Batch Operating System groups similar jobs into "batches" and executes them sequentially without manual intervention. Users submit jobs to an operator, who batches them and feeds them to the computer.

Limitation: Lack of user interaction. Once a job is submitted, the user must wait for it to finish; if it enters an infinite loop or requires input, the CPU may idle, and debugging is extremely difficult.

System Calls

System Calls provide the programming interface between a user application and the operating system services. They act as a bridge allowing user programs to request privileged operations (like reading a file) from the OS kernel.

Categories:

  1. Process Control: fork(), exit()
  2. File Management: open(), read(), write()
  3. Device Management: ioctl(), read() from device

Working of Interrupt-Driven I/O and state why it is more efficient than Programmed I/O

In Interrupt-Driven I/O, the CPU issues an I/O command to a device controller and immediately resumes executing other tasks. When the device controller finishes reading/writing the data, it sends a hardware interrupt to the CPU. The CPU briefly pauses its current work, processes the data, and resumes.

Efficiency: It eliminates "busy waiting" (polling). The CPU does not waste cycles constantly checking if the device is ready, allowing for true concurrent execution.

Hospital requires a system where every task must be completed within a strict deadline, or the result is considered useless even if computed correctly

A Hard Real-Time Operating System is required.

Justification: Hard real-time systems guarantee that critical tasks complete on time. In a hospital (e.g., a pacemaker or life-support system), missing a deadline can result in death. Other OS types like Time-Sharing prioritize fairness over strict deadlines, which would be fatal here.

Company wants to build a highly available server that must keep running even if one entire machine in the setup fails completely

They should choose a Clustered System.

Justification: A clustered system consists of multiple independent, fully complete machines (nodes) connected via a network. If one entire machine loses power or hardware fails completely, the other machines in the cluster detect this and take over its workload (High Availability). A multiprocessor system would still fail completely if its shared motherboard or power supply died.

Trace the sequence of steps that occur when a user application issues a request to read a file from the disk, starting from the System Call up to the return of control to the user program
  1. The user application makes a read() System Call.
  2. The CPU switches to Kernel Mode via a software trap.
  3. The OS asks the Device Controller (disk) to fetch the file.
  4. The CPU switches to another process while waiting (Interrupt-driven I/O).
  5. The disk finishes and sends a Hardware Interrupt to the CPU.
  6. The OS copies the data into the user program's memory.
  7. The OS switches back to User Mode and returns control to the application.
Justify why modern Operating Systems such as Linux use a Module-Based structure instead of a purely Monolithic or purely Microkernel structure

Modern systems use a Hybrid / Loadable Kernel Module (LKM) structure to get the best of both worlds:

  • Performance (Like Monolithic): Modules are loaded directly into the kernel space, meaning there is no slow message-passing overhead like in Microkernels.
  • Flexibility (Like Microkernel): The core kernel remains small. Device drivers and file systems can be loaded dynamically at runtime without rebooting the system or recompiling the entire monolithic kernel.
Any five functions of an Operating System, giving one relevant example for each function
  1. Process Management: Allocating CPU time. Ex: Pausing a background download to give priority to a video call.
  2. Memory Management: Managing RAM. Ex: Moving unused application data to virtual memory (swap) so a new heavy game can load into RAM.
  3. File Management: Organizing data. Ex: Saving a document and ensuring it is written to the correct physical sector on the SSD.
  4. Device Management: Handling I/O. Ex: Using a driver to translate a mouse movement into an on-screen cursor movement.
  5. Security & Protection: Enforcing access rules. Ex: Preventing a standard user from deleting critical System32 files.
Different types of Operating Systems — Batch, Multiprogramming, Time-Sharing, and Real-Time — along
  • Batch OS: Jobs with similar needs are batched and executed sequentially by an operator. Feature: No user interaction during execution.
  • Multiprogramming OS: Keeps multiple jobs in memory. When one job waits for I/O, the CPU switches to another. Feature: Maximizes CPU utilization.
  • Time-Sharing OS: An extension of multiprogramming. The CPU switches so rapidly (time-slicing) between tasks that multiple users feel they have dedicated machines. Feature: High interactivity and fairness.
  • Real-Time OS: Processes data instantly within guaranteed deadlines. Feature: Strict timing constraints (used in aviation, medical devices).
Five categories of System Calls
  1. Process Control: Create, terminate, or suspend processes. Ex: fork() to create a child process.
  2. File Management: Create, read, write, or delete files. Ex: read() to read bytes from a text file.
  3. Device Management: Request/release devices and read/write to them. Ex: ioctl() to configure a network interface.
  4. Information Maintenance: Get or set system data. Ex: gettimeofday() to fetch the current system time.
  5. Communication: Create connections or send messages between processes. Ex: pipe() to connect the output of one process to another.
Dual-Mode operation of an Operating System

Dual-Mode Operation provides hardware-level protection by dividing execution into User Mode (Bit=1) and Kernel Mode (Bit=0). Privileged instructions (like halting the CPU or direct hardware I/O) can only execute in Kernel Mode.

How they work together:
If a malicious user program runs in User Mode, it cannot directly crash the hardware because it lacks privileges. However, it could write an infinite loop to hog the CPU forever. This is where the Timer steps in. The OS configures the hardware timer before switching to User Mode. When the timer hits zero, it triggers an interrupt. The hardware forces the mode bit to 0 (Kernel Mode) and hands control back to the OS, which can then safely kill the malicious looping program.

Different Operating System structures — Simple, Monolithic, Layered, Microkernel, and Module-Based — highlighting one advantage and one disadvantage of each
  • Simple (MS-DOS): No clear separation between user/kernel modes. Adv: Fast, low overhead. Disadv: Highly vulnerable to crashes.
  • Monolithic (Early Linux): Entire OS is one giant kernel program. Adv: High performance via direct function calls. Disadv: Hard to debug and maintain.
  • Layered: OS divided into strict hierarchy layers. Adv: Easy to debug top-down. Disadv: Too much overhead passing data through multiple layers.
  • Microkernel (Mach): Minimal kernel; services run in user space. Adv: Extremely stable and secure. Disadv: Slow due to constant message passing.
  • Module-Based (Modern Linux/Windows): Core kernel loads object files dynamically. Adv: Flexible and fast. Disadv: A buggy module can still crash the kernel.
University wants to set up a computer lab where many students run their programs at the same time, each getting a quick, fair share of CPU time so the system feels interactive to everyone

The suitable OS is a Time-Sharing Operating System.

Justification: Time-Sharing is designed specifically for interactivity among multiple users. It uses CPU scheduling and multiprogramming to provide each user with a small portion of a time-shared computer. The CPU switches from one student's program to the next extremely rapidly (e.g., every 100 milliseconds). Because the switching is so fast, every student gets immediate response times and feels as though they have their own dedicated computer, satisfying the "interactive" and "fair share" requirements.

Company's server crashes frequently because a bug in a single device driver brings down the entire kernel, since the system uses a Monolithic structure

Proposed Solution: A Microkernel Architecture.

By moving the device drivers out of the privileged kernel space and running them as standard user-level processes, a bug or crash in the device driver will only kill that specific process. The Microkernel itself remains isolated and untouched, meaning the server will not crash.

Trade-offs: The primary disadvantage is Performance Overhead. Because the driver is now in user space, communicating with it requires Inter-Process Communication (IPC) and constant context switching between User Mode and Kernel Mode, which slows the system down compared to the direct function calls of a Monolithic kernel.

Trace a complete scenario: a user clicks 'Print' on a document
  1. The Word processor (in User Mode) issues a write() System Call to send data to the printer.
  2. A trap occurs, changing the mode bit to 0, switching execution to Kernel Mode.
  3. The OS kernel verifies permissions and sends the print command to the Printer's Device Controller.
  4. The OS puts the Word processor in a waiting state and switches the CPU back to User Mode to run other programs while the printer works.
  5. The Printer Controller prints the page. Once finished, it sends a Hardware Interrupt to the CPU.
  6. The CPU switches back to Kernel Mode, processes the interrupt, and marks the Word processor as ready to resume.
  7. The OS switches back to User Mode and control returns to Word, notifying the user it finished.
Critically analyze the statement: "Every Operating System structure involves trade-offs; there is no single best structure

The statement is completely accurate because structural design always balances performance against maintainability/security.

  • Monolithic: Offers peak performance but sacrifices modularity and stability (one bug crashes everything).
  • Microkernel: Offers peak stability and security (services are isolated) but sacrifices performance (massive IPC overhead).

Why Linux uses a Hybrid/Module approach: Modern OSs like Linux and Windows recognize these extremes are untenable. A Loadable Kernel Module (LKM) approach keeps the core kernel tightly integrated for Monolithic-like performance, while allowing drivers to be dynamically loaded/unloaded like a Microkernel. This achieves the "best of both worlds"—excellent speed without requiring a system reboot every time a new device is connected.

Unit II: Process Management

Process

A Process is a program in execution. It is an active entity.

Difference: A program is a passive entity (a file containing code stored on disk). A process is active; it has a program counter specifying the next instruction to execute, and associated resources (memory, registers).

Process Control Block (PCB)

A Process Control Block (PCB) is a data structure in the OS kernel containing all the information needed to manage a specific process. It acts as the repository for any information that may vary from process to process (e.g., process state, program counter, CPU registers, memory limits).

Context Switching

Context Switching is the mechanism where the OS saves the state (context) of the currently running process into its PCB and loads the saved state of another process from its PCB, allowing the CPU to switch execution from one process to another seamlessly.

User Thread and a Kernel Thread
User ThreadKernel Thread
Managed by a user-level thread library.Managed directly by the OS kernel.

Preemptive and Non-Preemptive Scheduling, giving one example algorithm for each
  • Non-Preemptive: Once a process gets the CPU, it holds it until it terminates or blocks for I/O. The OS cannot force it off the CPU. Example: First-Come, First-Served (FCFS).
  • Preemptive: The OS can forcefully interrupt a running process and give the CPU to another process (e.g., based on priority or time quantum). Example: Round Robin (RR).
Ready Queue and the Waiting (Blocked) Queue

The Ready Queue contains processes that reside in main memory and are fully ready and waiting to be assigned to the CPU. The Waiting Queue contains processes that cannot execute right now because they are waiting for a specific event to occur, such as an I/O completion or receiving a message.

While you are typing in MS Word, spell check runs in the background

The spell-checking routine acts as a User Thread. It cannot run directly on the CPU because the CPU hardware only executes OS Kernel Threads. To execute, the User Thread must be mapped onto a Kernel Thread (using models like Many-to-One or Many-to-Many) so the OS scheduler can actually assign it to a physical CPU core.

Process is running on the CPU when a timer interrupt occurs

The mechanism is Context Switching, initiated by the Short-Term Scheduler (CPU Scheduler) and executed by the Dispatcher.

In a Priority Scheduling system, process P2 is repeatedly skipped because new higher-priority processes keep arriving

P2 is facing Starvation (Indefinite Blocking). The solution to this problem is Aging, where the OS gradually increases the priority of a process the longer it waits in the ready queue.

Process has Arrival Time = 2 and Completion Time = 10,
  • Turnaround Time (TAT) = Completion Time - Arrival Time = 10 - 2 = 8.
  • Waiting Time (WT) = Turnaround Time - Burst Time = 8 - 6 = 2.
List and briefly explain the five states in the process life cycle
  1. New: The process is being created.
  2. Ready: The process is waiting to be assigned to a processor.
  3. Running: Instructions are being executed on the CPU.
  4. Waiting (Blocked): The process is waiting for some event to occur (e.g., I/O completion).
  5. Terminated: The process has finished execution.
Any three attributes stored in a Process Control Block (PCB)
  • Process State: The current status of the process (New, Ready, Running, Waiting).
  • Program Counter: The memory address of the very next instruction the CPU must execute for this process.
  • CPU Registers: Saves the contents of accumulators, index registers, and general-purpose registers so execution can resume seamlessly after an interrupt.
List the three types of process schedulers and state the function of each
  • Long-Term Scheduler (Job Scheduler): Selects processes from the disk and loads them into memory for execution, controlling the Degree of Multiprogramming.
  • Short-Term Scheduler (CPU Scheduler): Selects a process from the Ready Queue and allocates the CPU to it. Runs very frequently.
  • Medium-Term Scheduler: Swaps processes out of memory to disk and later swaps them back in to relieve memory pressure and improve the process mix.
Difference between Multiprogramming and Time-Sharing as objectives of process scheduling
  • Multiprogramming Objective: To maximize CPU utilization. The scheduler ensures the CPU is never idle by switching to a new process only when the current one blocks for I/O.
  • Time-Sharing Objective: To maximize interactivity and response time. The scheduler uses a time quantum to rapidly preempt processes, allowing multiple users to interact with the system simultaneously without noticeable lag.
Why Context Switching is necessary, listing any three situations in which it occurs

Context Switching is necessary because a single CPU core can only execute one process at a time. To provide the illusion of multitasking, the OS must rapidly swap processes in and out, saving their state so they can resume exactly where they left off.

Situations:

  1. A hardware interrupt occurs (e.g., a key is pressed).
  2. A process's time quantum expires in a Time-Sharing system.
  3. A process makes a blocking System Call (e.g., requesting to read a file).

  • Scheduling: Switching between Chrome and the music player (OS performs context switching via the CPU scheduler).

  • Medium-Term Scheduler: Responsible for swapping the process out temporarily to the disk when waiting for I/O, freeing up RAM for other processes, and swapping it back in later.
Process has Arrival Time = 0 and Burst Time = 8, but its execution actually starts at time = 3

Response Time: Time of first CPU access - Arrival Time = 3 - 0 = 3.

Reason for waiting: The CPU was currently occupied by another process that either arrived earlier (FCFS) or had a higher priority/shorter burst time, so this process had to wait in the Ready Queue until the CPU became available.

'user thread' created for spell-check in a Word application actually gets executed by the CPU, given that the CPU can run only kernel threads

The CPU hardware only knows about Kernel Threads. A User Thread (like spell-check) is created purely in user space by a thread library. To execute it, the library must map it to a Kernel Thread.

  1. The user library creates the spell-check thread.
  2. The library maps this thread to an available Kernel Thread using a multi-threading model (e.g., Many-to-One or Many-to-Many).
  3. The OS scheduler schedules that specific Kernel Thread onto a physical CPU core.
  4. When the Kernel Thread runs, it executes the code of the user thread mapped to it.
Complete process life cycle, describing all five states (New, Ready, Running, Waiting, Terminated) and the transitions between them
  • New: The process is being loaded into memory but isn't ready to execute. Transition: Admitted to Ready queue.
  • Ready: Residing in memory, waiting for CPU time. Transition: Scheduler dispatches it to Running.
  • Running: Instructions are actively being executed on the CPU. Transitions:
    • Interrupt (e.g., time slice expires) → Returns to Ready.
    • I/O Request → Moves to Waiting.
    • Exit → Moves to Terminated.
  • Waiting (Blocked): Waiting for an external event like user input. Transition: I/O completes → Moves back to Ready.
  • Terminated: Execution complete, OS reclaims memory.
Four major operations performed on a process — creation, scheduling, execution, and termination —
  1. Creation: The OS allocates a PCB and memory. Ex: Double-clicking the Photoshop icon.
  2. Scheduling: The OS decides which ready process gets the CPU next. Ex: The OS pausing a background anti-virus scan to let you type smoothly in Word.
  3. Execution: The CPU actively processes instructions. Ex: Rendering a video frame.
  4. Termination: The process ends and resources are freed. Ex: Clicking the 'X' to close your web browser.
Any five CPU scheduling algorithms (FCFS, SJF, SRTF, Round Robin, Priority Scheduling), covering the key characteristic and one limitation of each
  1. FCFS (First-Come, First-Served): Non-preemptive. Executes processes in arrival order. Limitation: Convoy effect (short processes stuck behind a massive one).
  2. SJF (Shortest Job First): Non-preemptive. Picks the process with the shortest burst time. Limitation: Impossible to know exact burst time in advance.
  3. SRTF (Shortest Remaining Time First): Preemptive version of SJF. Limitation: Can cause starvation for long processes.
  4. Round Robin: Preemptive. Assigns a fixed time quantum to each process in turn. Limitation: High context-switching overhead if quantum is too small.
  5. Priority Scheduling: Executes highest priority process first. Limitation: Starvation of low-priority processes (solved by aging).

Objectives/criteria of CPU scheduling (CPU utilization, throughput, turnaround time, waiting time, response time, fairness), and describe why some of these criteria can conflict
  • CPU Utilization: Keep the CPU as busy as possible (0-100%).
  • Throughput: Number of processes completed per time unit.
  • Turnaround Time: Total time from submission to completion.
  • Waiting Time: Total time spent waiting in the ready queue.
  • Response Time: Time from submission until the first response is produced.

Conflicts: Minimizing Response Time requires preempting processes frequently (Time-Sharing/Round Robin). However, frequent preemption causes high context-switching overhead, which severely decreases Throughput and CPU Utilization. You cannot optimize both simultaneously.

Consider three processes: P1 (AT=0, BT=5), P2 (AT=1, BT=3), P3 (AT=2, BT=8)

Using First Come First Serve (FCFS):

  • P1 arrives at 0. Executes 0 to 5. CT = 5. TAT = 5 - 0 = 5. WT = 5 - 5 = 0.
  • P2 arrives at 1. Waits till 5. Executes 5 to 8. CT = 8. TAT = 8 - 1 = 7. WT = 7 - 3 = 4.
  • P3 arrives at 2. Waits till 8. Executes 8 to 16. CT = 16. TAT = 16 - 2 = 14. WT = 14 - 8 = 6.

Average Waiting Time: (0 + 4 + 6) / 3 = 3.33

In a multi-core system, a web browser remains responsive overall even when one tab freezes because of a heavy script running in it, while other tabs keep working normally

A modern browser uses a Multithreaded / Multiprocess architecture. Instead of running the entire browser as a single-threaded process, it assigns a separate thread (or entire process) to each tab.

Because these are Kernel Threads (or separate processes), the OS CPU Scheduler manages them independently. If Tab A gets stuck in an infinite script loop, its specific thread maxes out one CPU core. However, the OS continues scheduling Tab B's thread onto a different core (or preempts Tab A to give Tab B time). Thus, the frozen tab does not block the UI or the other tabs.

Student's laptop feels slow to respond when opening a new file because too many background applications are competing for the CPU

The criterion most affected is Response Time.

Suggested Algorithm: Round Robin (RR).

Justification: If the laptop is using an algorithm like FCFS or non-preemptive priority, background tasks might hog the CPU for long continuous bursts, causing the UI to freeze. Round Robin preemptively slices CPU time (e.g., every 10ms) and distributes it evenly across all processes. This guarantees that the UI thread gets frequent access to the CPU, drastically improving interactive responsiveness, even if the total completion time (throughput) decreases slightly.

Critically compare FCFS, SJF, SRTF, Round Robin, and Priority Scheduling algorithms, and justify which algorithm would be most appropriate for (a) a batch processing system

(a) Batch Processing System: SJF (Shortest Job First) is most appropriate. Without user interaction, we don't care about fast response times. SJF mathematically guarantees the minimum average waiting time for a given set of processes, maximizing overall throughput and efficiency for heavy background workloads.

(b) Interactive Time-Sharing System: Round Robin (RR) is most appropriate. Multiple users require the system to feel "alive" and responsive. RR guarantees that every user's process receives a CPU time slice frequently, ensuring low Response Time and high fairness, preventing any single heavy user from monopolizing the system.

Unit III: Concurrency

Concurrency

Concurrency is the execution of multiple instruction sequences at the same time. It happens when multiple threads or processes make progress overlapping in time, either through rapid context switching (single-core) or true parallel execution (multi-core).

Example: Downloading a file in a web browser while simultaneously scrolling through a webpage.

Critical Section

A Critical Section is a specific segment of code in a process where shared resources (like shared memory, variables, or files) are accessed and modified. To prevent data corruption, no two processes can be executing their critical sections simultaneously.

Atomic operation

An Atomic Operation is an operation that executes entirely as a single, indivisible step. Once it starts, it cannot be interrupted or preempted halfway through.

Importance: It guarantees that shared variables (like locks or counters) are updated safely without race conditions caused by a mid-instruction context switch.

  • Binary Semaphore (Mutex): Can only take values 0 or 1. Used strictly to enforce mutual exclusion for a single critical section.
  • Counting Semaphore: Can take any non-negative integer value. Used to control access to a resource pool with multiple identical instances (e.g., managing 5 available printers).
Wait() and signal() operations of a semaphore
  • wait() (or P/down): Decrements the semaphore value. If the value becomes negative (or reaches 0 in a binary semaphore), the calling process is blocked and placed in a waiting queue.
  • signal() (or V/up): Increments the semaphore value. If there are processes blocked in the waiting queue, one is woken up and moved to the ready queue.

Two models of Inter-Process Communication (IPC)
  1. Shared Memory: Two processes establish a region of shared RAM. They communicate by reading and writing to this shared region directly. Fast, but requires explicit synchronization (e.g., semaphores) by the programmer.
  2. Message Passing: Processes communicate by sending and receiving messages through the OS kernel. Slower (due to system calls), but safer and easier to use in distributed systems.
And briefly explain the three requirements of a solution to the Critical-Section Problem
  1. Mutual Exclusion: If process P1 is executing in its critical section, no other process can enter theirs.
  2. Progress: If no process is in the critical section and some processes want to enter, the selection of the next process cannot be postponed indefinitely.
  3. Bounded Waiting: There must be a limit on how many times other processes can enter the critical section after a process has requested entry.
List the four sections into which the code of a process is logically divided to control access to the critical section, and briefly describe each
  1. Entry Section: The code requesting permission to enter the critical section (e.g., acquiring a lock).
  2. Critical Section: The code where shared resources are accessed.
  3. Exit Section: The code releasing the permission/lock, allowing others to enter.
  4. Remainder Section: The rest of the non-critical code.

Why high-level statements like counter++ and counter-- are not safe in a concurrent environment, referring to their internal machine-level steps

A high-level statement like counter++ is not an atomic operation. At the machine level, it breaks down into three distinct instructions:

  1. Load counter from memory into a CPU register.
  2. Increment the register.
  3. Store the register back to memory.

If a context switch occurs right after step 1 or 2, another process might load the old, stale value of counter. When both processes eventually complete step 3, one will overwrite the other's update, causing a Race Condition.

Peterson's Solution uses the flag[] array and the turn variable together to satisfy Mutual Exclusion, Progress, and Bounded Waiting for two processes

  • Progress: If P1 doesn't want to enter, flag[1] is false, so P0 can enter immediately without being indefinitely postponed.
  • Bounded Waiting: When P0 exits, it sets flag[0]=false. This immediately allows P1 (who might be waiting) to enter. P0 cannot re-enter and starve P1 because P0 will set turn=1 upon re-requesting, forcing itself to wait for P1.
Producer–Consumer problem

The Producer-Consumer problem occurs when two processes share a fixed-size buffer. The Producer generates data and puts it into the buffer; the Consumer takes data out.

Shared Variables:

  • buffer[BUFFER_SIZE]: A circular array.
  • in: The index where the next item will be inserted.
  • out: The index where the next item will be consumed.
  • counter: Tracks the total number of items currently in the buffer.

The Role / Rules: The Producer must not try to insert data when counter == BUFFER_SIZE (buffer is full). The Consumer must not try to remove data when counter == 0 (buffer is empty). Synchronization is required to ensure counter++ and counter-- do not create a race condition.

Peterson's Solution in detail, including its shared variables, working, and how it satisfies the requirements of the Critical-Section Problem

Peterson's Solution is a software-based synchronization algorithm for two processes (P0 and P1).

Shared Variables:

  • boolean flag[2] = {false, false}; (Indicates if a process wants to enter).
  • int turn; (Indicates whose turn it actually is).

Working (Code for P0):
flag[0] = true;
turn = 1; // Be polite, offer turn to P1
while (flag[1] == true && turn == 1); // Wait if P1 wants it AND it's P1's turn
...Critical Section...
flag[0] = false; // Exit

Requirements Satisfied: It guarantees Mutual exclusion (only one process can have turn == its_id), Progress (a process only waits if the other actively wants to enter), and Bounded waiting (the turn variable acts as a strict alternator, preventing starvation).

Semaphores in detail — their two fundamental operations (wait and signal), their types (counting and binary), and their disadvantages (busy waiting and possibility of deadlock)

A Semaphore (S) is an integer variable accessed only through two atomic operations:

  • wait(S): while(S <= 0); S--; (Waits until S > 0, then decrements it).
  • signal(S): S++; (Increments S).

Types:

  1. Binary (Mutex): S is 0 or 1. Used for mutual exclusion.
  2. Counting: S can be any integer. Used to manage a pool of identical resources.

Disadvantages:

  • Busy Waiting (Spinlock): Standard semaphores waste CPU cycles looping endlessly in wait() if the lock isn't free.
  • Deadlock: If two processes hold one semaphore each and wait for the other's, they freeze forever.
Three requirements of a solution to the Critical-Section Problem — Mutual Exclusion, Progress, and Bounded Waiting — describing the significance of each
  1. Mutual Exclusion: Absolute prevention of simultaneous access. Significance: If P1 is writing to a bank balance variable, P2 cannot read or write to it, preventing corrupted math.
  2. Progress: If the critical section is empty, processes that wish to enter cannot be blocked forever by processes executing in their remainder sections. Significance: Ensures the system doesn't freeze just because nobody is currently using the shared resource.
  3. Bounded Waiting: A bound must exist on the number of times other processes are allowed to enter their critical sections after a process has made a request to enter its own. Significance: Prevents starvation. P1 shouldn't have to wait forever while P2 rapidly enters and exits 100 times.
Working of the Test-and-Set Lock hardware synchronization mechanism, and evaluate which requirements of the Critical-Section Problem it satisfies and which it does not

Test-and-Set is an atomic hardware instruction. It reads the current value of a boolean variable (lock) and instantly sets it to true, entirely without interruption.

while (TestAndSet(&lock)) { 
    // do nothing (spin wait) 
}
// Critical Section
lock = false;

Evaluation:

  • Mutual Exclusion: YES. Because it is atomic, only the first process to execute it will see false and proceed; all others will see true and get stuck in the while loop.
  • Progress: YES. When the lock is released, a waiting process will immediately grab it.
  • Bounded Waiting: NO. There is no queue. If multiple processes are spinning, the hardware might arbitrarily keep giving the lock to P1 over and over, starving P2.

Step-by-Step Insertion:

  1. Producer executes wait(empty). empty decrements from 2 to 1. (Checks if there is space).
  2. Producer executes wait(mutex). mutex becomes 0. (Locks the buffer for exclusive access).
  3. Producer inserts the new item into the buffer.
  4. Producer executes signal(mutex). mutex becomes 1. (Unlocks the buffer).
  5. Producer executes signal(full). full increments from 3 to 4. (Notifies the Consumer that a new item is available).
Hospital's patient database is read by many doctors at the same time but updated by only one nurse at a time; while a nurse is updating a record, no doctor should be able to read stale or partial data

Variables Required:

  • mutex (initialized to 1): Protects the readcount variable.
  • wrt (initialized to 1): The main lock for the database, preventing Writers from entering if anyone is inside.
  • readcount (initialized to 0): Number of active doctors (readers).

Reader Logic (Doctors):

  • Entry Section: The doctor executes wait(mutex) to safely increment readcount. If this doctor is the very first reader (readcount == 1), they execute wait(wrt) to lock out all nurses (writers). They then signal(mutex) to let other doctors in.
  • Exit Section: The doctor executes wait(mutex) to safely decrement readcount. If they are the very last reader leaving (readcount == 0), they execute signal(wrt), finally unlocking the database so a waiting nurse can update it.
Five philosophers sit at a round table

Deadlock Scenario: If all 5 philosophers execute wait(left_fork) simultaneously, they all grab one fork. When they execute wait(right_fork), they find it's already held by their neighbour. They all wait infinitely for a right fork that will never be released (Circular Wait).

Solutions:

  1. Limiting Participants: Allow at most 4 philosophers to sit at the 5-seat table. This guarantees at least one philosopher will have access to two forks, break the cycle, finish eating, and release their forks.
  2. Asymmetric Solution: Number the philosophers. Even-numbered philosophers must pick up their left fork first, while odd-numbered philosophers must pick up their right fork first. This breaks the circular wait condition.
Critically analyze why Peterson's Solution and the Test-and-Set Lock, though correct in theory, are considered insufficient for modern operating systems, and explain how Semaphores and Monitors provide a more practical and scalable synchronization mechanism, referencing the classical synchronization problems (Bounded Buffer, Readers–Writers, Dining Philosophers) as supporting evidence

Why Peterson's / Test-and-Set are insufficient:

  1. Busy Waiting: They rely on while(true) spin-loops. This wastes massive amounts of CPU cycles just checking a lock, which is catastrophic in modern multitasking systems.
  2. Scalability: Peterson's solution mathematically only works for exactly two processes. Scaling it to 100 processes is incredibly complex.

Why Semaphores / Monitors are better:
Semaphores and Monitors use Blocking Queues instead of busy waiting. If a process cannot enter, the OS puts it to sleep (Waiting State) and switches the CPU to useful work.
In the Bounded Buffer problem, counting semaphores trivially manage $N$ slots of data without spin-loops. In the Readers-Writers problem, semaphores scale effortlessly to allow 100 readers simultaneously. Monitors take this a step further by removing manual wait/signal logic entirely, preventing the catastrophic deadlocks commonly seen if a developer makes a mistake coding the Dining Philosophers problem.
