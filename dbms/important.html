Q122. What is a transaction? Explain the ACID properties with the help of a bank transfer example.

Unit III CO3 | Bloom L2 5 Marks Midterm Score: 10.0

A transaction is a logical unit of work consisting of one or more SQL statements that must be executed entirely or not at all.

ACID Properties (Bank Transfer Example: A to B):

  • Atomicity: "All or nothing." If money is deducted from A, it MUST be credited to B. If either fails, the entire transaction is rolled back.
  • Consistency: The database must remain in a valid state. The total sum of A + B's balances must be the same before and after the transaction.
  • Isolation: Concurrent transactions do not interfere with each other. If another transaction reads A's balance during the transfer, it will see the state either strictly before or strictly after, not midway.
  • Durability: Once the transaction is committed, the changes are permanent and will survive system crashes.

Q118. Construct a B+ tree in which every node can hold at most 3 keys (a maximum of 4 child pointers) by inserting the keys 10, 20, 30, 40, 50, 60 and 70 in the given order. Show the tree after every node split and state two advantages of a B+ tree over a B-tree.

Unit IV CO4 | Bloom L3 5 Marks End Term Score: 9.8

Node Specification: Max keys $M = 3$, maximum child pointers $P = 4$. A node splits when the number of keys reaches 4.

Step-by-Step Construction:

  • Insert 10, 20, 30: All fit in the single root leaf node: [10, 20, 30].
  • Insert 40 (Split 1): Node overflows to [10, 20, 30, 40]. In a B+ tree leaf split, the middle key (index $\lceil 4/2 \rceil = 2$, key 30) is copied up to the parent. Left leaf keeps [10, 20], right leaf keeps [30, 40] with a leaf sibling pointer. New root becomes [30].
  • Insert 50: Placed into right leaf: [30, 40, 50]. Tree valid.
  • Insert 60 (Split 2): Right leaf overflows to [30, 40, 50, 60]. Leaf splits: left leaf retains [30, 40], right leaf gets [50, 60], and key 50 is copied up to root. Root now contains keys [30, 50].
  • Insert 70: Placed into rightmost leaf: [50, 60, 70]. Node is full but does not exceed 3 keys.

Two Distinct Advantages of a B+ Tree over a Standard B-Tree:

  • Extremely Fast Sequential Range Queries: In a B+ tree, all leaf nodes are linked into a continuous linked list. Range queries execute by jumping to the start key via root search and simply scanning linearly across leaf sibling pointers, completely avoiding expensive in-order tree traversals required by B-trees.
  • Higher Fanout and Lower Tree Height: Internal nodes in a B+ tree store only search keys and child pointers without actual data records. Consequently, each fixed-size disk page fits significantly more branch pointers (higher fanout), making the tree shallower and drastically reducing the number of disk I/O operations required for lookups.

As numbers are inserted, leaves split whenever they exceed 3 keys, pushing middle values up to form the root [30, 50]. The final leaves are [10, 20] → [30, 40] → [50, 60, 70], chained together like a train. B+ trees beat B-trees because leaves form a linked list for easy range scanning, and internal nodes fit more keys per disk page.

Q150. Analyse the trade-offs of the CAP theorem for a distributed database during a network partition. Using this analysis, justify whether a CP or an AP design is more suitable for (i) an online banking ledger and (ii) a social-media news feed, and explain how sharding and replication help a NoSQL system to scale.

Unit V CO5 | Bloom L4 5 Marks End Term Score: 9.7

1. CAP Theorem Trade-Off Analysis during Network Partition:

The CAP theorem states that a distributed system cannot simultaneously guarantee Consistency ($C$), Availability ($A$), and Partition Tolerance ($P$). Because physical network partitions ($P$) (cable cuts, packet loss, hardware switch failures) are unavoidable in distributed architectures, systems must choose between Consistency or Availability when a partition occurs:

  • CP (Consistency + Partition Tolerance): Rejects the read/write request on the isolated partition to prevent stale or conflicting data, returning an error or timeout. Sacrifices Availability to preserve absolute mathematical correctness.
  • AP (Availability + Partition Tolerance): Returns the locally available value (even if stale) and accepts writes locally. Sacrifices immediate Consistency to guarantee 100% Availability.

2. Application Justifications:

  • (i) Online Banking Ledger: CP Design (e.g., Google Spanner, MongoDB with majority write concern).
    Justification: Financial ledgers require zero tolerance for dirty reads, phantom withdrawals, or double-spending. If a network partition prevents verifying account balances across branches, the system must abort the transaction rather than serve incorrect monetary balances.
  • (ii) Social-Media News Feed: AP Design (e.g., Apache Cassandra, Amazon DynamoDB).
    Justification: User experience demands seamless, uninterrupted availability. If a user sees a friend's post or like count 5 seconds late due to a network partition, the business impact is negligible compared to showing a broken error screen.

3. How Sharding and Replication Enable NoSQL Scaling:

  • Sharding (Horizontal Scale-Out): Splits massive collections into disjoint ranges based on a shard key, distributing storage and write throughput across dozens of commodity servers.
  • Replication (High Availability & Read Scaling): Maintains identical copies across nodes, eliminating single points of failure and distributing read query loads geographically.

When network wires snap, you must pick: CP locks down and throws an error to prevent wrong numbers (essential for banking where double-spending is illegal); AP keeps answering with slightly outdated posts (perfect for social media where staying online matters more than seeing a tweet 2 seconds late). Sharding splits data across disks to scale writes, while replication copies data to scale reads.

Q8. Explain, with an example, the three levels of data abstraction in a DBMS.

Unit I CO1 | Bloom L2 3 Marks End Term Score: 9.6

The ANSI/SPARC Three-Schema Architecture divides database abstraction into three distinct levels:

  1. Physical (Internal) Level: The lowest level describing how data is actually stored in hardware (e.g., records stored in 4KB disk blocks with B+ tree indexes).
  2. Conceptual (Logical) Level: The middle level describing what data is stored and the relationships among them (e.g., Student(RollNo, Name, Email) where RollNo is primary key).
  3. View (External) Level: The highest level describing only part of the database relevant to specific user groups, hiding unnecessary details (e.g., student view displays only personal grades, concealing other students' data).

Quick Recall:

  • Physical Level: How data is stored on disk (bytes, blocks, B+ trees).
  • Conceptual Level: What data is stored (tables, columns, keys, relations).
  • View Level: Customized screens/subsets tailored for end users.

    • (Order_ID, Product_ID)+ = {Order_ID, Product_ID, Quantity, Product_Name, Customer_ID, Customer_Name}

Q23. Consider R(Student, Course, Instructor) with the functional dependencies {Student, Course -> Instructor; Instructor -> Course}. Find the candidate keys, check whether R is in 3NF and BCNF, decompose it into BCNF, and state whether the decomposition preserves the dependencies.

Unit I CO1 | Bloom L3 5 Marks End Term Score: 9.6

Given: $R(Student, Course, Instructor)$ and $F = \{Student, Course \rightarrow Instructor;\, Instructor \rightarrow Course\}$.

1. Candidate Keys:

  • $(Student, Course)^+ = \{Student, Course, Instructor\}$
  • $(Student, Instructor)^+$: Using $Instructor \rightarrow Course$, $(Student, Instructor)^+ = \{Student, Instructor, Course\}$.
  • Both are minimal super keys. Candidate Keys: (Student, Course) and (Student, Instructor).
  • Prime attributes: Student, Course, Instructor. (All attributes are prime).

2. Check 3NF and BCNF:

  • 3NF Check: A dependency $X \rightarrow Y$ satisfies 3NF if $X$ is a super key OR $Y$ is a prime attribute.
    • $Student, Course \rightarrow Instructor$: LHS is a super key. (Valid in 3NF and BCNF)
    • $Instructor \rightarrow Course$: LHS ($Instructor$) is NOT a super key, but RHS ($Course$) is a prime attribute. Hence, R is in 3NF.
  • BCNF Check: BCNF requires that for every $X \rightarrow Y$, $X$ must be a super key. In $Instructor \rightarrow Course$, $Instructor$ is not a super key. R is NOT in BCNF.

3. Decomposition into BCNF:

Decompose along the violating dependency $Instructor \rightarrow Course$:

  • $R_1(Instructor, Course)$ with $F_1 = \{Instructor \rightarrow Course\}$. Candidate key: $Instructor$. (In BCNF)
  • $R_2(Student, Instructor)$ with Candidate key: $(Student, Instructor)$. (In BCNF)

4. Dependency Preservation:

  • $F_1 \cup F_2$ contains $Instructor \rightarrow Course$, but the original dependency $Student, Course \rightarrow Instructor$ cannot be checked without joining $R_1$ and $R_2$.
  • The BCNF decomposition is Lossless, but DOES NOT preserve the functional dependency $Student, Course \rightarrow Instructor$.

Quick Recall: Candidate keys: (Student, Course) and (Student, Instructor). Relation is in 3NF (Course is prime) but NOT in BCNF (Instructor is not super key). BCNF split: R1(Instructor, Course) and R2(Student, Instructor). Lossless, but NOT dependency preserving.

🎯 Evaluator Scoring Keywords:
3NF vs BCNF Candidate Keys Prime attributes BCNF Decomposition Dependency Preservation

Q50. Using Student(sid, sname, age, city), Course(cid, cname, credits) and Enrollment(sid, cid, grade), write SQL queries to (i) find students enrolled in the maximum number of courses, (ii) find courses that have no 'F' grades recorded, (iii) compute average credits taken per student, and (iv) list courses with total enrollment higher than the average enrollment across all courses.

Comprehensive SQL solutions:

    SELECT s.sid, s.sname, COUNT(e.cid) AS total_courses
FROM Student s
JOIN Enrollment e ON s.sid = e.sid
GROUP BY s.sid, s.sname
HAVING COUNT(e.cid) = (
    SELECT MAX(cnt) FROM (
        SELECT COUNT(cid) AS cnt FROM Enrollment GROUP BY sid
    ) AS t
);
  2. (ii) Courses with NO 'F' grades recorded:
    SELECT cid, cname
FROM Course
WHERE cid NOT IN (
    SELECT cid FROM Enrollment WHERE grade = 'F'

    SELECT AVG(total_cred) AS avg_credits_per_student

    GROUP BY e.sid

        SELECT COUNT(sid) AS cnt FROM Enrollment GROUP BY cid
    ) AS avg_tbl
);

Q80. For the table ACCOUNT(Acc_No, Name, Balance), write a stored procedure (MySQL or PL/SQL) Transfer_Funds(from_acc, to_acc, amount) that transfers amount between accounts, verifying that from_acc has sufficient balance, and using transaction commands COMMIT and ROLLBACK.

Unit III CO3 | Bloom L3 5 Marks End Term Score: 9.6

Stored procedure implementing transactional fund transfer with balance checks in MySQL:

DELIMITER $$

CREATE PROCEDURE Transfer_Funds(
    IN  p_from_acc INT,
    IN  p_to_acc   INT,
    IN  p_amount   DECIMAL(12, 2)
)
proc_body: BEGIN
    DECLARE v_from_balance DECIMAL(12, 2);
    DECLARE v_to_exists    INT DEFAULT 0;
    
    -- Error handler to automatically rollback on any SQL error
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SELECT 'Transaction Failed: System Error encountered. Rolled back.' AS Result;
    END;

    -- Start explicit transaction
    START TRANSACTION;

    -- 1. Check sender balance with row lock (FOR UPDATE)
    SELECT Balance INTO v_from_balance
    FROM ACCOUNT
    WHERE Acc_No = p_from_acc
    FOR UPDATE;

    IF v_from_balance IS NULL THEN
        ROLLBACK;
        SELECT 'Transfer Failed: Source account does not exist.' AS Result;
        LEAVE proc_body;
    END IF;

    IF v_from_balance < p_amount THEN
        ROLLBACK;
        SELECT 'Transfer Failed: Insufficient funds in source account.' AS Result;
        LEAVE proc_body;
    END IF;

    -- 2. Check destination account existence
    SELECT COUNT(*) INTO v_to_exists
    FROM ACCOUNT
    WHERE Acc_No = p_to_acc;

    IF v_to_exists = 0 THEN
        ROLLBACK;
        SELECT 'Transfer Failed: Destination account does not exist.' AS Result;
        LEAVE proc_body;
    END IF;

    -- 3. Execute transfer
    UPDATE ACCOUNT SET Balance = Balance - p_amount WHERE Acc_No = p_from_acc;
    UPDATE ACCOUNT SET Balance = Balance + p_amount WHERE Acc_No = p_to_acc;

    -- Commit atomic transfer
    COMMIT;
    SELECT 'Transfer Successful: Funds transferred and committed.' AS Result;
END $$

DELIMITER ;

Quick Recall: Starts transaction, locks sender row via FOR UPDATE, checks balance and receiver existence. Deducts from sender, adds to receiver, and calls COMMIT. Calls ROLLBACK on any error or insufficient balance.

Stored Procedure START TRANSACTION COMMIT ROLLBACK FOR UPDATE Fund Transfer ACID Atomicity

Q105. With an example, explain the ACID properties of a transaction.

Unit IV CO4 | Bloom L2 3 Marks End Term Score: 9.6

ACID properties guarantee reliable database transactions. Consider transferring ₹1,000 from account $A$ to account $B$:

  • Atomicity: All operations succeed or none do. Either both debiting $A$ and crediting $B$ succeed, or the transaction aborts and leaves both balances unchanged.
  • Consistency: The transaction transforms the database from one valid state to another, preserving integrity invariants (e.g., total funds $A + B$ remains constant before and after).
  • Isolation: Intermediate states are hidden from concurrent transactions. Another transaction reading $A$ and $B$ cannot see $A$ deducted before $B$ is credited.
  • Durability: Once committed, updates persist permanently on non-volatile storage, even if a power failure or system crash occurs immediately afterward.

Atomicity = All or nothing. Consistency = Total money stays correct. Isolation = No one sees your transfer halfway done. Durability = Once confirmed, power cuts cannot erase the transfer.

Q113. Explain shared (S) and exclusive (X) locks along with the lock compatibility matrix, and describe the basic two-phase locking protocol, including its growing phase, shrinking phase and lock point.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.6

Lock-based concurrency control protocols restrict concurrent data access using complementary lock modes and acquisition phases:

1. Shared (S) and Exclusive (X) Locks:

  • Shared Lock ($S$): Read-only lock mode. If a transaction holds a shared lock on data item $Q$, other concurrent transactions can also acquire shared locks on $Q$ ($S-S$ is compatible). No writes are permitted.
  • Exclusive Lock ($X$): Read-write lock mode. Only one transaction can hold an exclusive lock on $Q$ at any given moment ($X-S$ and $X-X$ are strictly incompatible).

2. Two-Phase Locking (2PL) Protocol:

The basic 2PL protocol guarantees conflict serializability by requiring every transaction to separate its lock operations into two distinct, non-overlapping phases:

  • Phase 1: Growing (Expanding) Phase: The transaction acquires new locks as needed and may upgrade locks ($S \to X$). It cannot release any lock under any circumstances.
  • Lock Point: The exact instant when the transaction acquires its final lock (reaches peak lock count). The chronological order of lock points across transactions dictates their exact conflict serialization order.
  • Phase 2: Shrinking (Contracting) Phase: The transaction releases held locks and may downgrade locks ($X \to S$). It cannot acquire any new locks once this phase begins.

Serializability Guarantee: Because transactions never acquire new locks after releasing an earlier lock, no circular data item dependencies can be created, proving that 2PL guarantees conflict serializability.

A Shared lock is like reading a public book (everyone can read). An Exclusive lock is like writing in your private diary (only one person allowed). In 2PL, you gather all keys during the growing phase until your 'lock point', and once you return even one key (shrinking phase), you can never pick up another key again.

Q125. State the CAP theorem and name its three properties.

Brewer's CAP Theorem states that any distributed data store can simultaneously guarantee at most two out of three properties in the presence of network partitions.

Its three core properties are:

  • Consistency (C): Every read receives the most recent write or an error.
  • Availability (A): Every non-failing node returns a non-error response for every request (without guaranteeing latest data).
  • Partition Tolerance (P): The system continues to operate despite arbitrary network message losses or node network isolations.

The CAP theorem says you can't have it all in a distributed network. When cables snap (Partition), you must choose: either freeze until data synchronizes (Consistency) or keep answering with possibly stale data (Availability).

Q148. Explain replication in MongoDB with reference to the primary and secondary members of a replica set, the election of a new primary when the current primary fails, and write concern. State the benefits of replication.

Unit V CO5 | Bloom L2 5 Marks End Term Score: 9.6

Replication in MongoDB provides redundancy, high availability, and automated failover across distributed nodes.

1. Replica Set Architecture:

  • Primary Member: Exactly one primary accepts all write operations, recording changes in a capped collection called the oplog (operations log).
  • Secondary Members: Secondaries continuously read the primary's oplog and apply operations asynchronously to replicate data state. They can serve read queries if configured.
  • Arbiter (Optional): A lightweight voting-only member that holds no data, used solely to break election ties in clusters with even node counts.

2. Election of a New Primary:

Members send heartbeat pings every 2 seconds. If secondaries receive no response from the primary within 10 seconds, an election is triggered. Secondaries nominate eligible members based on member priority and oplog recency; the node holding the most up-to-date oplog that wins a strict majority of votes becomes the new Primary.

3. Write Concern:

Write concern specifies the level of acknowledgement requested from MongoDB for write operations:

  • { w: 1 }: Acknowledged by Primary only (fast, but data could be lost if primary fails before replication).
  • { w: "majority" }: Acknowledged only after the write is committed to a majority of replica set nodes, preventing rollback during failover.
  • { j: true }: Ensures the operation is written to on-disk journal before returning acknowledgement.

4. Benefits of Replication:

Guarantees continuous 24/7 high availability, eliminates single points of failure, allows zero-downtime rolling maintenance/upgrades, and offloads heavy analytical read traffic from the primary node. Strong write concerns (such as w: 'majority') protect mission-critical applications against data rollbacks if a primary node suddenly experiences ungraceful hardware failure before replication completes.

In MongoDB replication, the Primary receives all writes and logs them in its oplog, while Secondaries copy the log. If the Primary goes down, nodes vote in a new Primary in seconds. Write Concern lets you choose between fast writes (acknowledged by primary only) or ultra-safe writes (acknowledged by a majority of servers). It guarantees 24/7 uptime without data loss.

Q9. Explain multivalued dependency and the fourth normal form (4NF) with an example.

Unit I CO1 | Bloom L2 3 Marks End Term Score: 9.5

A Multivalued Dependency (MVD), denoted as $X \twoheadrightarrow Y$, occurs when the presence of one or more rows in a table implies the presence of certain other rows, representing an independent multi-valued relationship between attributes.

Formally, in relation $R(X, Y, Z)$, $X \twoheadrightarrow Y$ means that for a given value of $X$, the set of $Y$ values depends solely on $X$ and is completely independent of $Z$.

Fourth Normal Form (4NF): A relation is in 4NF if and only if:

  1. It is already in Boyce-Codd Normal Form (BCNF).
  2. For every non-trivial MVD $X \twoheadrightarrow Y$, $X$ is a super key of the relation.

Example: Consider Teacher_Skill_Hobby(Teacher, Skill, Hobby) where a teacher has multiple independent skills and multiple independent hobbies:

TeacherSkillHobby
Dr. SharmaJavaCricket
Dr. SharmaJavaMusic
Dr. SharmaPythonCricket
Dr. SharmaPythonMusic

Here, Teacher ->> Skill and Teacher ->> Hobby. Teacher alone is not a super key, causing redundant Cartesian product rows. Decomposing into R1(Teacher, Skill) and R2(Teacher, Hobby) satisfies 4NF.

Quick Recall: 4NF eliminates independent multi-valued facts mixed in one table. A relation is in 4NF if in BCNF and every MVD $X \twoheadrightarrow Y$ has $X$ as a super key. Solved by splitting into two independent tables.

Q60. Consider the relation R(A, B, C) with the functional dependency set F = {A -> B}. Analyse whether the decomposition into R1(A, B) and R2(B, C) is (i) lossless join, and (ii) dependency preserving. Justify your answer using Heath's theorem and the definition of dependency preservation.

Unit II CO2 | Bloom L3 5 Marks End Term Score: 9.5

Given: $R(A, B, C)$, $F = \{A \rightarrow B\}$, decomposed into $R_1(A, B)$ and $R_2(B, C)$.

1. Lossless Join Analysis (Heath's Theorem):

  • Heath's Theorem states that a binary decomposition of $R$ into $R_1$ and $R_2$ is lossless if and only if the common attribute set ($R_1 \cap R_2$) functionally determines either $R_1$ or $R_2$, i.e.:$$(R_1 \cap R_2) \rightarrow R_1 \quad \text{OR} \quad (R_1 \cap R_2) \rightarrow R_2$$
  • Here, $R_1 \cap R_2 = \{B\}$.
  • We compute the attribute closure of the common attribute $B$ with respect to $F$:$$B^+ = \{B\}$$
  • Since $B^+$ does not contain $A$ ($B \not\rightarrow A$) and does not contain $C$ ($B \not\rightarrow C$), $B$ is NOT a super key of either $R_1$ or $R_2$.
  • Conclusion: The decomposition is LOSSY (Not Lossless)! Joining $R_1 \bowtie R_2$ will generate spurious tuples.

2. Dependency Preservation Analysis:

  • $F_1 = \pi_{R_1}(F) = \{A \rightarrow B\}$ (since both $A, B \in R_1$).
  • $F_2 = \pi_{R_2}(F) = \emptyset$.
  • $(F_1 \cup F_2)^+ = \{A \rightarrow B\}^+ = F^+$.
  • Conclusion: The decomposition IS DEPENDENCY PRESERVING.

Quick Recall: Common attribute is $B$. Since $B^+ = \{B\}$, $B$ is not a super key of $R_1$ or $R_2$. By Heath's theorem, the decomposition is LOSSY (spurious tuples). However, $A \rightarrow B$ is preserved in $R_1$, so it is dependency preserving.

Q112. Explain how deadlocks are detected using a wait-for graph, and explain the deadlock recovery schemes: victim selection, rollback and the avoidance of starvation.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.5

A deadlock occurs in lock-based concurrency control when transactions enter circular wait states for held locks.

1. Deadlock Detection via Wait-For Graph (WFG):

A Wait-For Graph is a directed graph $G = (V, E)$ maintained dynamically by the lock manager where vertices $V$ represent active transactions and directed edge $T_i \to T_j$ indicates that $T_i$ is suspended waiting for a lock currently held by $T_j$. When a lock request cannot be granted, an edge is added; when a lock is released, corresponding edges are deleted.

The lock manager invokes cycle-detection algorithms (e.g., Depth-First Search or Tarjan's strongly connected components algorithm) at scheduled intervals. A deadlock exists if and only if the WFG contains a directed cycle.

2. Deadlock Recovery Schemes:

  • Victim Selection: When a cycle is detected, the DBMS chooses one transaction in the cycle to abort. The selection minimizes overall rollback overhead based on criteria such as elapsed execution time, remaining queries, number of modified rows, and number of cascading rollbacks prevented.
  • Rollback Policy:
    • Total Rollback: Abort the victim completely and restart it from the very beginning.
    • Partial Rollback: Roll back the victim only to an intermediate savepoint sufficient to release the contested lock and break the graph cycle, saving prior computational work.
  • Avoidance of Starvation: If victim selection always chooses the youngest transaction or the one with the fewest updates, that transaction could repeatedly be aborted and starved from ever finishing. To prevent starvation, the DBMS associates an abort count with each transaction; each abort increments its priority so an older transaction is never starved indefinitely.

The DBMS draws arrows between transactions showing who is waiting for whom. If the arrows form a closed circle, it is a deadlock. To break it: (1) Pick a 'victim' transaction that is cheap to abort, (2) Roll it back (partially or totally) to release its locks, and (3) Ensure the same transaction isn't picked repeatedly so it doesn't starve forever.

Q30. The relation SPJ(Supplier, Part, Project) satisfies the join dependency that it is the join of its projections (Supplier, Part), (Part, Project) and (Project, Supplier). 1. Join Dependency (JD) & Fifth Normal Form (5NF):

  • A relation $R$ satisfies the Join Dependency $\bowtie(R_1, R_2, \dots, R_n)$ if and only if $R$ is equal to the natural join of its projections $R_1, R_2, \dots, R_n$.
  • Fifth Normal Form (5NF / Project-Join Normal Form): A relation is in 5NF if and only if it is in 4NF and every non-trivial join dependency $\bowtie(R_1, R_2, \dots, R_n)$ in $R$ is implied by the candidate keys of $R$ (i.e., every $R_i$ contains a candidate key of $R$).

2. Why SPJ is not in 5NF:

  • In SPJ(Supplier, Part, Project), the only candidate key is the composite key (Supplier, Part, Project).
  • The business rule states that whenever Supplier $S$ supplies Part $P$, Part $P$ is used in Project $J$, and Supplier $S$ supplies Project $J$, then $S$ MUST supply $P$ to $J$. This cyclic constraint is a non-trivial Join Dependency: $\bowtie((Supplier, Part), (Part, Project), (Project, Supplier))$.
  • Since none of the projections $(Supplier, Part)$, $(Part, Project)$, or $(Project, Supplier)$ is a super key of SPJ, SPJ violates 5NF.

3. Decomposition into 5NF:

Decompose into three binary projection relations:

  1. SP(Supplier, Part)
  2. PJ(Part, Project)
  3. JS(Project, Supplier)

4. Lossless Reconstruction & Redundancy Removal:

  • Storing binary projections eliminates cyclic redundant combinations and avoids spurious tuples during three-way join.
  • The natural join $SP \bowtie PJ \bowtie JS$ exactly reconstructs the original valid ternary tuples without information loss.

Quick Recall: 5NF deals with Join Dependencies that cannot be captured by binary MVDs. SPJ is decomposed into 3 binary projections: SP(Supplier, Part), PJ(Part, Project), and JS(Project, Supplier). Three-way join is completely lossless.

Q98. Draw the state diagram of a transaction and explain each of its states.

Unit IV CO4 | Bloom L2 3 Marks End Term Score: 9.4

During its lifecycle, a database transaction progresses through several distinct execution states to guarantee ACID properties and system consistency:

  • Active: The initial execution state where the transaction begins and executes its read and write database operations.
  • Partially Committed: Entered immediately after the final statement has executed, but updates still reside in memory buffers and have not yet been flushed to stable disk storage.
  • Failed: Entered when normal execution cannot proceed due to hardware failures, logical errors, or concurrency violations.
  • Aborted: The transaction is rolled back, all dirty updates are undone, and the database is restored to its pre-transaction state. The transaction can either restart or terminate.
  • Committed: Entered when all log records and updates are permanently recorded on stable storage, guaranteeing durability.

A transaction starts Active. When code finishes, it is Partially Committed until written to disk, then Committed. If an error occurs anywhere, it goes to Failed and gets Aborted (rolled back).

Q111. Explain recoverable, non-recoverable and cascadeless schedules and cascading rollback, giving a short example schedule for each.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.4

Transaction recovery properties define how concurrent schedules behave when uncommitted dependencies encounter unexpected failures or aborts:

1. Non-Recoverable Schedule:

Occurs when transaction $T_2$ reads a data item modified by uncommitted transaction $T_1$, and $T_2$ commits before $T_1$. If $T_1$ subsequently aborts, $T_2$ has committed dirty data that cannot be rolled back without violating the Durability property of ACID.

Example: $S_1: W_1(A), R_2(A), Commit(T_2), Abort(T_1)$. Once $T_2$ commits, its results are permanently written to disk, leaving the database in an unrecoverable corrupted state.

2. Recoverable Schedule:

A schedule is recoverable if, whenever transaction $T_2$ reads a data item written by transaction $T_1$, the commit operation of $T_1$ precedes the commit operation of $T_2$ ($Commit(T_1) < Commit(T_2)$).

Example: $S_2: W_1(A), R_2(A), Commit(T_1), Commit(T_2)$. If $T_1$ aborts instead, $T_2$ has not yet committed and can be safely aborted too.

3. Cascading Rollback:

A phenomenon where the failure and rollback of a single transaction triggers a chain reaction of aborts across multiple dependent, uncommitted transactions that read its dirty uncommitted updates.

Example: $S_3: W_1(A), R_2(A), W_2(B), R_3(B), Abort(T_1)$. Because $T_1$ aborts, $T_2$ must abort, which in turn forces $T_3$ to abort, squandering significant CPU and disk I/O work.

4. Cascadeless Schedule:

A schedule is cascadeless (avoids cascading aborts) if every transaction reads only values written by already committed transactions ($Read_j(X)$ is delayed until after $Commit(T_i)$).

Example: $S_4: W_1(A), Commit(T_1), R_2(A), Commit(T_2)$. Since $T_2$ only reads after $T_1$ commits, an abort of $T_1$ can never affect $T_2$. Every cascadeless schedule is strictly recoverable.

Containment Hierarchy: The classes of schedules satisfy the strict inclusion relation: $\text{Strict Schedules} \subset \text{Cascadeless Schedules} \subset \text{Recoverable Schedules} \subset \text{All Possible Schedules}$. Commercial database engines enforce cascadelessness or strictness to maintain continuous system throughput.

Non-recoverable: You commit work based on someone else's uncommitted notes, and they delete their draft (disaster). Recoverable: You wait for them to submit before you submit. Cascading rollback: One person's mistake forces ten other people to scrap their work. Cascadeless: Nobody is allowed to read a note until it is officially submitted and approved.

Q117. Explain the deadlock prevention schemes Wait-Die and Wound-Wait with examples.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.4

Deadlock prevention protocols use transaction timestamps to decide whether a requesting transaction should wait or abort when a resource conflict occurs. Monotonic timestamp $TS(T_i)$ is assigned when transaction $T_i$ begins (smaller timestamp implies older transaction).

Suppose transaction $T_i$ requests a lock held by transaction $T_j$:

1. Wait-Die Scheme (Non-Preemptive):

  • Older requests from Younger ($TS(T_i) < TS(T_j)$): $T_i$ is allowed to wait.
  • Younger requests from Older ($TS(T_i) > TS(T_j)$): $T_i$ dies (aborts) and restarts with its original timestamp.
  • Rule Summary: 'Old waits, young dies.' Locks are never preemptively stolen.
  • Example: Let $TS(T_1)=10$ (older) and $TS(T_2)=20$ (younger). If $T_1$ requests a lock held by $T_2$, $T_1$ waits. If $T_2$ requests a lock held by $T_1$, $T_2$ dies and restarts.

2. Wound-Wait Scheme (Preemptive):

  • Older requests from Younger ($TS(T_i) < TS(T_j)$): $T_i$ wounds $T_j$; $T_j$ is preempted, aborted, and rolls back, releasing its lock to $T_i$. $T_j$ restarts with its original timestamp.
  • Younger requests from Older ($TS(T_i) > TS(T_j)$): $T_i$ is allowed to wait.
  • Rule Summary: 'Old wounds, young waits.' Younger transactions are preempted by older ones.
  • Example: With $TS(T_1)=10$ and $TS(T_2)=20$, if $T_1$ requests a lock held by $T_2$, $T_1$ preempts ($T_2$ is aborted). If $T_2$ requests a lock held by $T_1$, $T_2$ waits.

3. Key Comparison:

MetricWait-DieWound-Wait
PreemptionNon-preemptivePreemptive
Number of AbortsHigh (young transactions die repeatedly)Fewer aborts; locks granted quickly to old
StarvationAvoided (retains original timestamp)Avoided (retains original timestamp)

Starvation Freedom Guarantee: In both schemes, when an aborted transaction restarts, it keeps its original starting timestamp. Thus, as time passes, the transaction becomes progressively older relative to new transactions, guaranteeing that it eventually becomes the oldest active transaction and runs to completion without ever dying again.

Think of timestamps as age (older has priority). In Wait-Die: seniors are patient and wait for juniors, but if a junior asks a senior, the junior dies. In Wound-Wait: seniors don't wait; they wound and kick out juniors, while juniors patiently wait for seniors. Both prevent deadlock cycles.

Q102. Distinguish between conflict serializability and view serializability with an example.

Unit IV CO4 | Bloom L2 3 Marks End Term Score: 9.3

Serializability guarantees that concurrent schedules produce results identical to some serial execution:

  • Conflict Serializability: A schedule is conflict serializable if it can be transformed into a serial schedule by swapping non-conflicting concurrent operations. This holds if and only if its precedence (conflict) graph is acyclic. Tested efficiently in polynomial time $O(V + E)$.
  • View Serializability: A weaker, broader condition requiring identical initial reads, dependent reads, and final writes as some serial schedule. Testing view serializability is NP-complete.
  • Example: Consider schedule $S: R_1(A), W_2(A), W_1(A), W_3(A)$. Here, operations conflict in both directions ($T_1 \to T_2$ and $T_2 \to T_1$), producing a cycle in the precedence graph; thus $S$ is not conflict serializable. However, due to blind writes ($W_3(A)$ overwriting $A$), $S$ produces the exact same view as serial schedule $T_1 \to T_2 \to T_3$, making it view serializable.

Conflict serializability checks whether conflicting operations can be swapped without changing order (easy to test with graphs). View serializability is broader: it allows blind writes that overwrite values, matching final outputs even when conflicts exist.

Q116. Why is two-phase locking (mostly strict 2PL) used in commercial DBMSs? Show with an example schedule that it can still cause deadlock, and write its other drawbacks.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.3

Commercial database engines (such as Oracle, PostgreSQL, and SQL Server) overwhelmingly implement Strict Two-Phase Locking (Strict 2PL) as their primary concurrency control protocol.

1. Why Commercial DBMSs Adopt Strict 2PL:

  • Guarantees Serializability: Like basic 2PL, it mathematically guarantees that all concurrent interleaved schedules are conflict serializable.
  • Eliminates Cascading Aborts: By holding exclusive ($X$) locks until commit, transactions never write data that others read uncommitted; schedules are strictly cascadeless and recoverable.
  • Simple Crash Recovery: Transaction rollback requires only undoing before-images without inspecting or aborting other transactions.

2. Deadlock Schedule Example under Strict 2PL:

Strict 2PL does not prevent deadlocks. Consider two transactions $T_1$ and $T_2$ accessing data items $A$ and $B$:

  • $T_1$ acquires $X(A)$ and writes to $A$.
  • $T_2$ acquires $X(B)$ and writes to $B$.
  • $T_1$ requests $X(B)$: since $T_2$ holds $X(B)$ until commit, $T_1$ must wait for $T_2$.
  • $T_2$ requests $X(A)$: since $T_1$ holds $X(A)$ until commit, $T_2$ must wait for $T_1$.

Both transactions hold resources while waiting for each other ($T_1 \to T_2 \to T_1$), creating a mutual deadlock that requires DBMS intervention.

3. Drawbacks of Two-Phase Locking:

  • Deadlock Overhead: Systems must dedicate CPU cycles to maintain wait-for graphs, run cycle-detection routines, and abort/restart victims.
  • Reduced Concurrency & Lock Convoying: Long-running write transactions holding exclusive locks stall all subsequent readers and writers, degrading multi-user throughput.
  • Lock Maintenance Cost: Allocating, updating, and hashing lock table entries adds memory consumption and lock manager processing latency.
  • Phantom Anomalies: Tuple-level 2PL cannot stop phantom inserts into range queries unless expensive predicate/index-range locking is used.

Strict 2PL is popular because it guarantees safety and clean rollbacks without domino-effect cancellations. However, it can still cause deadlocks: if T1 locks A waiting for B, and T2 locks B waiting for A, they freeze. Its other downsides are lower concurrency, lock table memory overhead, and lock queues.

Q101. Explain the lost update and dirty read problems that arise when transactions execute concurrently, with an example of each.

Unit IV CO4 | Bloom L2 3 Marks End Term Score: 9.2

Concurrency anomalies occur when transactions interleave without adequate synchronization:

  • Lost Update (Write-Write Conflict): Occurs when two transactions read the same data item and subsequently update it based on the earlier read value. The second write overwrites and obliterates the first write without incorporating its modifications.
    Example: Account balance is ₹100. $T_1$ reads 100 and computes 150. Concurrently, $T_2$ reads 100 and computes 120. $T_1$ writes 150, then $T_2$ writes 120. $T_1$'s ₹50 deposit is completely lost.
  • Dirty Read (Read-Write Conflict): Occurs when transaction $T_2$ reads a data item modified by transaction $T_1$ that has not yet committed. If $T_1$ subsequently aborts, $T_2$ has acted on transient, invalid data.
    Example: $T_1$ updates balance from ₹100 to ₹500. $T_2$ reads ₹500 and approves a purchase. $T_1$ aborts and rolls back to ₹100. $T_2$'s read was 'dirty'.

Lost update: Two people book the last seat at the exact same second, and the second booking overwrites the first. Dirty read: Reading someone's draft before they delete it and change their mind.

Q114. Compare strict and rigorous two-phase locking with the help of an example, and state the benefits of each.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.2

Strict 2PL and Rigorous 2PL are specialized variants of the Two-Phase Locking protocol that enforce stronger guarantees than basic 2PL.

1. Strict Two-Phase Locking (Strict 2PL):

  • Rule: In addition to basic 2PL rules, a transaction must hold all its exclusive ($X$) locks until it terminates (commits or aborts). Shared ($S$) locks can be released during the shrinking phase before commit.
  • Benefits: Guarantees recoverable and cascadeless schedules (prevents dirty reads), simplifying transaction rollback without cascading aborts. Allows concurrent reads to proceed earlier when shared locks are released.

2. Rigorous Two-Phase Locking (Rigorous 2PL):

  • Rule: A transaction must hold all locks (both Shared $S$ and Exclusive $X$) until it terminates (commits or aborts). The shrinking phase collapses to the commit/abort point.
  • Benefits: Guarantees strict serializability. Transactions can be serialized in the exact order in which they commit, making schedule analysis and replication coordination straightforward.

3. Comparative Example Schedule:

Consider transaction $T_1$ needing to read $A$ and update $B$, and transaction $T_2$ needing to read $A$:

  • Under Strict 2PL: $T_1$ acquires $S(A)$ and $X(B)$. After reading $A$, $T_1$ can release $S(A)$ early. $T_2$ can immediately acquire $S(A)$ and read $A$ before $T_1$ commits. However, $T_1$ retains $X(B)$ until commit.
  • Under Rigorous 2PL: $T_1$ acquires $S(A)$ and $X(B)$. $T_1$ cannot release $S(A)$ until it commits. $T_2$ must wait if it needs an exclusive lock, ensuring strict chronological locking isolation.

Q135. Explain the BASE properties of NoSQL databases and contrast them briefly with ACID.

Unit V CO5 | Bloom L2 3 Marks End Term Score: 9.2

The BASE model governs distributed NoSQL systems, prioritizing horizontal availability over strict relational consistency:

  • Basically Available: The database system remains operational and accessible to clients at all times, even in the event of partial node or network partition failures.
  • Soft State: System state may fluctuate or drift over time even without client interaction, due to asynchronous replica propagation models.
  • Eventual Consistency: The system does not guarantee immediate consistency on every read, but guarantees that all replicas will eventually converge to identical states if no further updates occur.

Contrast with ACID:

  • Pessimistic vs. Optimistic: ACID enforces strict, immediate consistency and serializable isolation via pessimistic locking, causing operations to stall or fail during partitions.
  • Availability Priority: BASE embraces optimistic, relaxed consistency to guarantee uninterrupted availability ($A$) and partition tolerance ($P$) across large distributed clusters.

ACID is strict and conservative: every read must be immediately accurate, even if the system must freeze to do it. BASE is relaxed: it promises the system will always stay up (Basically Available) and data will catch up across servers after a brief delay (Eventual Consistency).

Q107. Explain log-based recovery with the deferred database modification and immediate database modification techniques.

Unit IV CO4 | Bloom L2 3 Marks End Term Score: 9.1

Log-based recovery uses a write-ahead log (WAL) on stable storage to restore database consistency after crashes:

  • Deferred Database Modification: All write operations update only the log buffer in memory; the actual database on disk is modified only after the transaction commits.
    Recovery Policy: Since uncommitted updates are never written to disk, an UNDO is never required (NO-UNDO/REDO algorithm). During crash recovery, the DBMS only REDOes transactions whose log contains both <T start> and <T commit>.
  • Immediate Database Modification: Database updates can be written to disk while the transaction is still active, before committing (following WAL rules).
    Recovery Policy: Requires both UNDO and REDO (UNDO/REDO algorithm). Uncommitted transactions that modified disk blocks must be UNDONE, while committed transactions must be REDONE to guarantee durability.

Deferred modification: Don't touch disk until commit. If crash occurs, no undo needed, only redo committed ones. Immediate modification: Changes hit disk anytime. If crash occurs, undo uncommitted transactions and redo committed ones.

Q109. Explain the unrepeatable read and phantom read problems of concurrent transactions with an example for each.

Unit IV CO4 | Bloom L2 3 Marks End Term Score: 9.0

These two read anomalies occur under relaxed SQL isolation levels:

  • Unrepeatable (Fuzzy) Read: Transaction $T_1$ reads a specific row. Concurrently, transaction $T_2$ modifies or deletes that row and commits. When $T_1$ re-reads the exact same row, it discovers that the values have changed or the row disappeared.
    Example: $T_1$ reads employee John's salary as ₹50,000. $T_2$ updates John's salary to ₹60,000 and commits. $T_1$ re-reads John's record and finds ₹60,000, violating read repeatability.
  • Phantom Read: Transaction $T_1$ reads a set of rows satisfying a search predicate. Concurrently, transaction $T_2$ inserts a new row matching that predicate and commits. When $T_1$ re-executes the query, a new 'phantom' row appears.
    Example: $T_1$ runs SELECT count(*) WHERE dept='IT' (gets 5). $T_2$ inserts a new IT employee and commits. $T_1$ re-runs the count and gets 6.

Unrepeatable read: A value inside an existing row changes between two reads. Phantom read: Brand new rows appear or vanish from a query range between two reads because another transaction inserted them.

Q138. Differentiate between insertOne and insertMany, updateOne and updateMany, and deleteOne and deleteMany in MongoDB, giving a one-line command for each.

Unit V CO5 | Bloom L2 3 Marks End Term Score: 9.0

MongoDB distinguishes between single-document and multi-document CRUD methods:

  • insertOne vs. insertMany:
    • insertOne inserts a single document into the collection.
      db.users.insertOne({ name: "Alice", age: 21 });
    • insertMany inserts an array of multiple documents in a single atomic batch call.
      db.users.insertMany([{ name: "Bob" }, { name: "Carol" }]);
  • updateOne vs. updateMany:
    • updateOne updates only the first matching document encountered in the collection.
      db.users.updateOne({ name: "Alice" }, { $set: { age: 22 } });
    • updateMany updates all documents in the collection that satisfy the query filter.
      db.users.updateMany({ dept: "HR" }, { $inc: { salary: 2000 } });
  • deleteOne vs. deleteMany:
    • deleteOne removes at most one document matching the specified criteria.
      db.users.deleteOne({ name: "Bob" });
    • deleteMany deletes every document satisfying the filter condition.
      db.users.deleteMany({ status: "inactive" });

Methods ending in One affect only the single first matching document (insert 1 document, update 1 document, delete 1 document). Methods ending in Many affect every matching document in bulk across the entire collection.
