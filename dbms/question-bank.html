Q1. What is a DBMS? Discuss its advantages over a traditional file-processing system.

Unit I CO1 | Bloom L2 2 Marks Midterm
Definition

A Database Management System (DBMS) is software that interacts with end-users, applications, and the database itself to capture and analyze data. It allows users to create, read, update, and delete data in a database.

Advantages over File-Processing
  • Data Redundancy and Inconsistency: Centralizes data, eliminating duplicate files and ensuring updates propagate everywhere.
  • Data Isolation: Applications do not need to know the physical structure of the data files.
  • Integrity Problems: Allows defining explicit integrity constraints (e.g., account balance > 0).
  • Security Problems: Offers fine-grained access control and user authorization.
  • Concurrent Access: Manages simultaneous access securely, preventing anomalies.

Q2. What do you mean by data redundancy and data inconsistency? How does a DBMS take care of these problems?

Unit I CO1 | Bloom L2 2 Marks Midterm
Definitions
  • Data Redundancy: The unnecessary duplication of data in a database. (e.g., storing a student's address in both the Library and Department files).
  • Data Inconsistency: A consequence of redundancy where different copies of the same data hold different values (e.g., address updated in Library but not Department).
DBMS Solution

A DBMS minimizes redundancy by storing a single, centralized copy of the data (Data Normalization). Because there is only one authoritative copy, inconsistency is inherently prevented.

Q3. Give the difference between a database system and a file-based system.

Unit I CO1 | Bloom L2 2 Marks Midterm
Differences
  • Structure: DB systems store data in structured formats (tables/graphs); File systems store data in plain text/binary files.
  • Data Independence: DB systems separate applications from data structure; File systems tightly couple applications to file formats.
  • Querying: DB systems provide robust query languages (SQL); File systems require custom application code to extract data.

Q4. Draw and explain the three-level (ANSI-SPARC) architecture of a DBMS.

Unit I CO1 | Bloom L2 2 Marks Midterm Score: 9
The Three Levels
  1. External Level (View Level): The highest level, describing only the part of the database relevant to a specific user group (hiding the rest).
  2. Conceptual Level (Logical Level): Describes what data is stored in the entire database and the relationships among those data. Used by DBAs.
  3. Internal Level (Physical Level): Describes exactly how the data is physically stored on disk (data structures, file organizations).
Exam Tip: The primary objective of this architecture is to achieve Data Independence.

Q5. What is data abstraction? Discuss the three levels of data abstraction used in a DBMS.

Unit I CO1 | Bloom L2 2 Marks Midterm
Definition

Data abstraction is the process of hiding complex internal data structures and storage details from the user, presenting only a simplified, usable view of the data.

Three Levels
  • Physical Level: Hides the complexity of block structures, indexing, and bytes on disk.
  • Logical Level: Hides physical storage but reveals entities, data types, and relationships. Developers interact here.
  • View Level: Hides the entire logical schema except for specific fields the end-user is authorized to see (e.g., a teller seeing only names and balances).

Q6. Define the terms schema and instance. Why is this distinction important?

Unit I CO1 | Bloom L1 2 Marks Midterm
Definition
  • Schema: The overall logical design/blueprint of the database. It changes rarely.
  • Instance: The snapshot of data residing in the database at a specific moment in time. It changes frequently.
Importance

This distinction is crucial for maintaining data independence—altering the schema (like adding a column) should not arbitrarily destroy the existing instances.

Q7. What is data independence? Explain logical and physical data independence with a suitable example.

Unit I CO1 | Bloom L2 2 Marks Midterm
Definition

Data independence is the ability to modify a schema definition in one level without affecting a schema definition in the next higher level.

Types
  • Physical Data Independence: Ability to modify the internal/physical schema without altering the conceptual schema. Example: Changing a file from sequential to a B+ tree index to improve performance; application code doesn't change.
  • Logical Data Independence: Ability to modify the conceptual schema without altering the external schema (user views). Example: Splitting an Employee table into two normalized tables; the original view can be maintained using a SQL JOIN, shielding the frontend application.

  • Application Programmers: Software engineers who write the backend logic connecting to the DB.
  • Sophisticated Users: Analysts who interact directly with the DB using SQL queries to generate reports.
  • Database Administrators (DBA): IT professionals who manage security, schemas, and performance tuning.

Q10. Compare the hierarchical, network, relational and object-oriented data models. Which one is most widely used today and why?

Unit I CO1 | Bloom L3 2 Marks Midterm
Comparison
  • Hierarchical: Data organized in a tree structure (1:N relationships). Fast but inflexible; requires navigating rigid pointers.
  • Network: Data organized in a graph (M:N relationships allowed). Highly complex and difficult to maintain.
  • Relational: Data organized in 2D tables (relations). Uses declarative SQL. Extremely flexible and mathematically sound.
  • Object-Oriented: Data stored as objects with methods, matching OOP languages. Best for complex data (e.g., CAD/CAM).
Most Widely Used

The Relational Model is most widely used today due to its simplicity, robust theoretical foundation (normalization), and standard interface (SQL) which provides unparalleled data independence.

Q11. State the advantages of the relational model over the other data models.

Unit I CO1 | Bloom L1 2 Marks Midterm
Advantages
  • Simplicity: Uses a simple tabular structure (rows and columns) that is easy to understand compared to complex graph/tree pointers.
  • Flexibility: Supports ad-hoc querying using standard SQL.
  • Data Independence: Strong separation between logical representation and physical storage.

Q12. Explain the terms super key, candidate key, primary key and foreign key with a suitable example.

Unit I CO1 | Bloom L2 2 Marks Midterm Score: 9
Explanation
  • Super Key: Any combination of columns that uniquely identifies a row. (e.g., StudentID + Name)
  • Candidate Key: A minimal super key; it uniquely identifies a row with no unnecessary columns. (e.g., StudentID or Email)
  • Primary Key: The specific candidate key chosen to identify rows. Cannot be NULL. (e.g., StudentID)
  • Foreign Key: A column that refers to the primary key of another table, enforcing referential integrity. (e.g., Dept_ID in a Student table referencing the Department table)

Q13. What are integrity constraints in a relational model? Explain domain, key, entity and referential integrity.

Unit I CO1 | Bloom L2 2 Marks Midterm
Definition

Integrity constraints are rules applied to a database to ensure the data is accurate, consistent, and valid.

The Four Constraints
  • Domain Constraint: Restricts the values a column can hold to a valid set (e.g., Age must be a positive integer).
  • Key Constraint: Ensures that candidate/primary keys are completely unique for every row.
  • Entity Integrity: States that no part of a Primary Key can be NULL, because a NULL value cannot uniquely identify a row.
  • Referential Integrity: States that if a foreign key exists in a relation, its value must either match a primary key value in the referenced relation or be NULL. (e.g., You cannot enroll a student in a non-existent Course_ID).

The Entity-Relationship (E-R) model is a high-level conceptual data model that visually represents entities (objects) and the relationships between them.

Notations
  • Rectangle: Entity sets
  • Ellipse: Attributes

Q15. Define entity, entity set, attribute and relationship, and illustrate each with a small diagram.

Unit I CO1 | Bloom L2 2 Marks Midterm
Definitions
  • Entity: A real-world object with independent existence (e.g., a specific student).
  • Entity Set: A collection of similar entities (e.g., all Students).
  • Attribute: A property describing an entity (e.g., Name, Age).
  • Relationship: An association among two or more entities (e.g., Student Enroll Course).

Q16. Explain the different types of attributes, simple, composite, derived, multivalued and key attribute, with examples.

Unit I CO1 | Bloom L2 3 Marks Midterm
Attribute Types
  • Simple: Indivisible atomic values (e.g., Gender).
  • Composite: Can be broken down into sub-parts (e.g., Name into First Name, Last Name).
  • Derived: Calculated from other attributes; not physically stored (e.g., Age derived from DOB).
  • Multivalued: Can hold multiple values for a single entity (e.g., Phone_Numbers).
  • Key: Uniquely identifies the entity (e.g., Roll_No).

Q17. What are the different types of relationships that can exist between two entities? Explain with diagrams.

Unit I CO1 | Bloom L2 3 Marks Midterm
Cardinality Ratios
  • One-to-One (1:1): One entity in A is associated with at most one in B. (e.g., Department 1:1 Manager).
  • One-to-Many (1:N): One entity in A is associated with many in B. (e.g., Department 1:N Employees).
  • Many-to-Many (M:N): Many entities in A associated with many in B. (e.g., Student M:N Course).

Q18. What is a weak entity set? Give a suitable example.

Unit I CO1 | Bloom L2 3 Marks Midterm
Definition

A weak entity set lacks sufficient attributes to form a primary key. It depends on a strong entity (identifying owner) and uses the owner's key plus its own partial key to identify rows.

Example

A Dependent (spouse/child) of an Employee. The dependent is identified by combining their Name (partial key) with the owner's Employee ID.

Q19. Explain unary, binary and ternary relationships with the help of diagrams.

Unit I CO1 | Bloom L2 3 Marks Midterm
Degrees of Relationships
  • Unary (Degree 1): Relationship between instances of a single entity set (e.g., Employee Manages Employee).
  • Binary (Degree 2): Relationship between two entity sets (e.g., Student Takes Course).
  • Ternary (Degree 3): Relationship connecting three entity sets simultaneously (e.g., Supplier Supplies Part To Project).
Exam Tip: A ternary relationship is not just three binary relationships; it represents a single fact involving all three entities together.

Q20. Differentiate between total participation and partial participation constraints in an E-R diagram.

Unit I CO1 | Bloom L2 3 Marks Midterm
Differentiation
  • Total Participation (Mandatory): Every entity MUST participate in at least one relationship. Indicated by a double line. (e.g., Every Employee must belong to a Department).
  • Partial Participation (Optional): Only some entities may participate. Indicated by a single line. (e.g., Only some Employees are Managers of a Department).

Q21. Explain generalization and specialization in the Extended E-R model with an example of each.

Unit I CO1 | Bloom L2 3 Marks Midterm
Specialization (Top-Down)

The process of defining a set of subclasses from a single entity type (the superclass). It involves identifying characteristics that distinguish some entities in the set from others.
Example: An Employee superclass can be specialized into Engineer, Manager, and Technician subclasses based on job role.

Generalization (Bottom-Up)

The reverse process of specialization. Multiple entity types with common attributes are synthesized into a single, generalized superclass.
Example: Car and Truck entities share attributes like Vehicle_ID and Price, so they can be generalized into a Vehicle superclass.

Q22. What is the difference between overlapping and disjoint specialization? Illustrate with an example.

Unit I CO1 | Bloom L2 3 Marks Midterm
Disjoint Specialization

An entity can be a member of at most one subclass of the specialization. Denoted by a 'd' in the circle.
Example: An Employee can be either an Hourly_Employee or a Salaried_Employee, but never both at the same time.

Overlapping Specialization

An entity may be a member of more than one subclass of the specialization. Denoted by an 'o' in the circle.
Example: A Person can simultaneously be an Alumnus and an Employee of a university.

Q23. What is aggregation in E-R modelling? When is it required? Explain with an example.

Unit I CO1 | Bloom L2 3 Marks Midterm
Definition

Aggregation is an abstraction where a relationship set (and its associated entities) is treated as a higher-level entity set.

When is it required?

The basic E-R model cannot express relationships among relationships. Aggregation is required when a relationship between two entities needs to participate in another relationship with a third entity.

Example

Consider Employee working on a Project. This forms the relationship Works_On. If we want to record the Manager who oversees this specific (Employee-Project) assignment, we aggregate Works_On into a single entity, and create a new relationship Manages between it and Manager.

Q24. Explain the concept of mapping cardinality with neat diagrams.

Unit I CO1 | Bloom L2 3 Marks Midterm
Definition

Mapping cardinality (or cardinality ratio) expresses the number of entities to which another entity can be associated via a relationship set.

Types
  • One-to-One (1:1): An entity in A is associated with at most one entity in B, and vice versa.
  • One-to-Many (1:N): An entity in A is associated with any number of entities in B. An entity in B is associated with at most one entity in A.
  • Many-to-One (N:1): An entity in A is associated with at most one entity in B. An entity in B is associated with any number of entities in A.
  • Many-to-Many (M:N): An entity in A is associated with any number of entities in B, and vice versa.

Q25. What is a functional dependency? Why is it important in the process of database design?

Unit I CO1 | Bloom L1 3 Marks Midterm
Definition

A functional dependency (FD) is a constraint between two sets of attributes in a relation. If A → B (A determines B), then for every valid instance of the relation, any two tuples that agree on the attribute A must also agree on the attribute B.

Importance

Functional dependencies are the theoretical bedrock of Normalization. They are used to specify constraints on data, discover candidate keys, and decompose relations to eliminate redundancy and update anomalies.

Q26. What are insertion, deletion and update anomalies? How does normalization help remove them?

Unit I CO1 | Bloom L2 3 Marks Midterm Score: 9
The Three Anomalies
  • Update Anomaly: If data is stored redundantly, changing it in one row requires changing it in all rows. Missing one causes inconsistency (e.g., changing a department's location).
  • Insertion Anomaly: The inability to add data to the database due to absence of other data (e.g., unable to add a new Department because it has no Employees yet, and Employee_ID is the primary key).
  • Deletion Anomaly: The unintended loss of data when deleting a row (e.g., deleting the only employee in a department also deletes the department's information).
How Normalization Helps

Normalization resolves these by decomposing large, poorly structured tables into smaller, well-structured tables where each table represents a single logical theme or entity. By linking them with foreign keys, redundancy is eliminated, which inherently solves update, insertion, and deletion anomalies.

Q27. What is normalization? Explain 1NF, 2NF and 3NF with a suitable example.

Unit I CO1 | Bloom L2 3 Marks Midterm Score: 9.5
Definition

Normalization is the process of organizing data to minimize redundancy and eliminate anomalies by dividing larger tables into smaller tables and defining relationships between them using functional dependencies.

The Normal Forms
  • First Normal Form (1NF): All attributes must be atomic (indivisible). No repeating groups or arrays allowed in a cell.
  • Second Normal Form (2NF): Must be in 1NF, and all non-key attributes must be fully functionally dependent on the entire primary key. (Eliminates partial dependencies).
  • Third Normal Form (3NF): Must be in 2NF, and no non-key attribute can be dependent on another non-key attribute. (Eliminates transitive dependencies: X → Y and Y → Z).

Q28. Define BCNF. How is it different from 3NF? Support your answer with an example.

Unit I CO1 | Bloom L2 3 Marks Midterm
Definition

Boyce-Codd Normal Form (BCNF) requires that for every non-trivial functional dependency X → Y, X must be a super key. It is a stronger, stricter version of 3NF.

Difference from 3NF

3NF allows a dependency X → Y where X is NOT a super key, provided that Y is a prime attribute (part of a candidate key). BCNF does not allow this exception. A table can be in 3NF but fail BCNF if it has overlapping candidate keys.

Example

Consider Relation(Student, Course, Instructor). Keys are (Student, Course) and (Student, Instructor). FD: Instructor → Course.
It is in 3NF because Course is a prime attribute. However, it violates BCNF because Instructor is not a super key.

Q29. Write a short note on 4NF and 5NF, with an example of each.

Unit I CO1 | Bloom L2 5 Marks Midterm
Fourth Normal Form (4NF)

Deals with Multi-valued Dependencies (MVD). A table is in 4NF if it is in BCNF and contains no non-trivial multi-valued dependencies (where one attribute determines a set of values for another, independent of a third).
Example: An Employee has multiple Skills and multiple Dependents. Storing them in one table creates massive redundancy. We split into (Emp, Skill) and (Emp, Dependent).

Fifth Normal Form (5NF)

Deals with Join Dependencies. Also known as Project-Join Normal Form (PJNF). A table is in 5NF if it is in 4NF and cannot be decomposed into smaller tables without losing data (lossless join). It ensures that all join dependencies are implied by candidate keys.

Q30. What is lossless-join decomposition? Explain with an example.

Unit I CO1 | Bloom L2 5 Marks Midterm
Definition

Lossless-join decomposition means that if a relation R is decomposed into R1 and R2, joining them back together via a Natural Join will yield the exact original relation R, without any missing rows (loss of data) or extra spurious rows (creation of invalid data).

Condition

The decomposition is lossless if the common attribute(s) between R1 and R2 form a super key for either R1 or R2. (i.e., R1 ∩ R2 → R1 OR R1 ∩ R2 → R2).

Example

Splitting Employee(ID, Name, Dept, Dept_Location) into Emp(ID, Name, Dept) and Department(Dept, Dept_Location) is lossless because their intersection, Dept, is a primary key for the Department table.

Q31. Define dependency-preserving decomposition and give a suitable example.

Unit I CO1 | Bloom L2 5 Marks Midterm
Definition

A decomposition is dependency-preserving if the union of the functional dependencies in the decomposed relations logically implies all the functional dependencies of the original relation. This ensures that updates can be checked for validity without joining the tables back together.

Example

Original Relation: R(A, B, C)
Functional Dependencies (FDs): A → B, B → C
Decomposition: R1(A, B) and R2(B, C).
FDs in R1: A → B.
FDs in R2: B → C.
Since (A → B) ∪ (B → C) covers all original FDs, it is a dependency-preserving decomposition.

Q77. What is decomposition? Explain the concepts of lossless-join and dependency-preserving decomposition.

Unit II CO2 | Bloom L2 5 Marks Midterm Score: 9.5

Decomposition is the process of breaking down a large, poorly-designed relation into two or more smaller relations to eliminate redundancy and anomalies.

Lossless-Join Decomposition

A decomposition of R into R1 and R2 is lossless if joining R1 and R2 back together using a Natural Join yields the exact original relation R, without generating spurious (fake) tuples.

Condition: The common attributes must be a candidate key for at least one of the decomposed relations (i.e., R1 ∩ R2 → R1 or R1 ∩ R2 → R2).

Dependency-Preserving Decomposition

A decomposition is dependency-preserving if all original functional dependencies can be checked and enforced using only the decomposed relations, without needing to join them back together.

Q133. What is meant by a recoverable schedule?

Q141. Explain the lost update and dirty read problems that arise when transactions execute concurrently, with an example of each.

Q142. Distinguish between conflict serializability and view serializability with an example.

Unit IV CO4 | Bloom L2 3 Marks End Term Score: 9.3

Serializability guarantees that concurrent schedules produce results identical to some serial execution:

  • Conflict Serializability: A schedule is conflict serializable if it can be transformed into a serial schedule by swapping non-conflicting concurrent operations. This holds if and only if its precedence (conflict) graph is acyclic. Tested efficiently in polynomial time $O(V + E)$.
  • View Serializability: A weaker, broader condition requiring identical initial reads, dependent reads, and final writes as some serial schedule. Testing view serializability is NP-complete.
  • Example: Consider schedule $S: R_1(A), W_2(A), W_1(A), W_3(A)$. Here, operations conflict in both directions ($T_1 \to T_2$ and $T_2 \to T_1$), producing a cycle in the precedence graph; thus $S$ is not conflict serializable. However, due to blind writes ($W_3(A)$ overwriting $A$), $S$ produces the exact same view as serial schedule $T_1 \to T_2 \to T_3$, making it view serializable.

Conflict serializability checks whether conflicting operations can be swapped without changing order (easy to test with graphs). View serializability is broader: it allows blind writes that overwrite values, matching final outputs even when conflicts exist.

Q143. Explain the role of the concurrency control manager and the lock manager, and describe how the lock table is used to grant or queue lock requests.

The concurrency control manager ensures serializability, isolation, and consistency across interleaved transactions. It delegates resource locking to the lock manager.

The lock manager maintains an in-memory hash table called the lock table, indexed by data item ID:

  • Granted List: Holds records of transactions currently granted a lock on the item, along with lock mode (Shared $S$ or Exclusive $X$).

The lock manager acts like a hotel receptionist with a key registry (lock table). If a room is free or multiple guests want to read only, keys are given out. If someone wants private access, later requests must wait in a queue.

Q151. Explain recoverable, non-recoverable and cascadeless schedules and cascading rollback, giving a short example schedule for each.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.4

Transaction recovery properties define how concurrent schedules behave when uncommitted dependencies encounter unexpected failures or aborts:

1. Non-Recoverable Schedule:

Occurs when transaction $T_2$ reads a data item modified by uncommitted transaction $T_1$, and $T_2$ commits before $T_1$. If $T_1$ subsequently aborts, $T_2$ has committed dirty data that cannot be rolled back without violating the Durability property of ACID.

Example: $S_1: W_1(A), R_2(A), Commit(T_2), Abort(T_1)$. Once $T_2$ commits, its results are permanently written to disk, leaving the database in an unrecoverable corrupted state.

2. Recoverable Schedule:

A schedule is recoverable if, whenever transaction $T_2$ reads a data item written by transaction $T_1$, the commit operation of $T_1$ precedes the commit operation of $T_2$ ($Commit(T_1) < Commit(T_2)$).

Example: $S_2: W_1(A), R_2(A), Commit(T_1), Commit(T_2)$. If $T_1$ aborts instead, $T_2$ has not yet committed and can be safely aborted too.

3. Cascading Rollback:

A phenomenon where the failure and rollback of a single transaction triggers a chain reaction of aborts across multiple dependent, uncommitted transactions that read its dirty uncommitted updates.

Example: $S_3: W_1(A), R_2(A), W_2(B), R_3(B), Abort(T_1)$. Because $T_1$ aborts, $T_2$ must abort, which in turn forces $T_3$ to abort, squandering significant CPU and disk I/O work.

4. Cascadeless Schedule:

A schedule is cascadeless (avoids cascading aborts) if every transaction reads only values written by already committed transactions ($Read_j(X)$ is delayed until after $Commit(T_i)$).

Example: $S_4: W_1(A), Commit(T_1), R_2(A), Commit(T_2)$. Since $T_2$ only reads after $T_1$ commits, an abort of $T_1$ can never affect $T_2$. Every cascadeless schedule is strictly recoverable.

Containment Hierarchy: The classes of schedules satisfy the strict inclusion relation: $\text{Strict Schedules} \subset \text{Cascadeless Schedules} \subset \text{Recoverable Schedules} \subset \text{All Possible Schedules}$. Commercial database engines enforce cascadelessness or strictness to maintain continuous system throughput.

Non-recoverable: You commit work based on someone else's uncommitted notes, and they delete their draft (disaster). Recoverable: You wait for them to submit before you submit. Cascading rollback: One person's mistake forces ten other people to scrap their work. Cascadeless: Nobody is allowed to read a note until it is officially submitted and approved.

Q152. Explain how deadlocks are detected using a wait-for graph, and explain the deadlock recovery schemes: victim selection, rollback and the avoidance of starvation.

Unit IV CO4 | Bloom L2 5 Marks End Term Score: 9.5

A deadlock occurs in lock-based concurrency control when transactions enter circular wait states for held locks.

1. Deadlock Detection via Wait-For Graph (WFG):

A Wait-For Graph is a directed graph $G = (V, E)$ maintained dynamically by the lock manager where vertices $V$ represent active transactions and directed edge $T_i \to T_j$ indicates that $T_i$ is suspended waiting for a lock currently held by $T_j$. When a lock request cannot be granted, an edge is added; when a lock is released, corresponding edges are deleted.

The lock manager invokes cycle-detection algorithms (e.g., Depth-First Search or Tarjan's strongly connected components algorithm) at scheduled intervals. A deadlock exists if and only if the WFG contains a directed cycle.

2. Deadlock Recovery Schemes:

  • Victim Selection: When a cycle is detected, the DBMS chooses one transaction in the cycle to abort. The selection minimizes overall rollback overhead based on criteria such as elapsed execution time, remaining queries, number of modified rows, and number of cascading rollbacks prevented.
  • Rollback Policy:
    • Total Rollback: Abort the victim completely and restart it from the very beginning.
    • Partial Rollback: Roll back the victim only to an intermediate savepoint sufficient to release the contested lock and break the graph cycle, saving prior computational work.
  • Avoidance of Starvation: If victim selection always chooses the youngest transaction or the one with the fewest updates, that transaction could repeatedly be aborted and starved from ever finishing. To prevent starvation, the DBMS associates an abort count with each transaction; each abort increments its priority so an older transaction is never starved indefinitely.

The DBMS draws arrows between transactions showing who is waiting for whom. If the arrows form a closed circle, it is a deadlock. To break it: (1) Pick a 'victim' transaction that is cheap to abort, (2) Roll it back (partially or totally) to release its locks, and (3) Ensure the same transaction isn't picked repeatedly so it doesn't starve forever.

Q157. Explain the deadlock prevention schemes Wait-Die and Wound-Wait with examples.

  • Older requests from Younger ($TS(T_i) < TS(T_j)$): $T_i$ is allowed to wait.
  • Younger requests from Older ($TS(T_i) > TS(T_j)$): $T_i$ dies (aborts) and restarts with its original timestamp.

  • Example: Let $TS(T_1)=10$ (older) and $TS(T_2)=20$ (younger). If $T_1$ requests a lock held by $T_2$, $T_1$ waits. If $T_2$ requests a lock held by $T_1$, $T_2$ dies and restarts.

  • Older requests from Younger ($TS(T_i) < TS(T_j)$): $T_i$ wounds $T_j$; $T_j$ is preempted, aborted, and rolls back, releasing its lock to $T_i$. $T_j$ restarts with its original timestamp.
  • Younger requests from Older ($TS(T_i) > TS(T_j)$): $T_i$ is allowed to wait.
  • Rule Summary: 'Old wounds, young waits.' Younger transactions are preempted by older ones.
  • Example: With $TS(T_1)=10$ and $TS(T_2)=20$, if $T_1$ requests a lock held by $T_2$, $T_1$ preempts ($T_2$ is aborted). If $T_2$ requests a lock held by $T_1$, $T_2$ waits.

Q174. Explain the BASE properties of NoSQL databases and contrast them briefly with ACID.

The BASE model governs distributed NoSQL systems, prioritizing horizontal availability over strict relational consistency:

  • Basically Available: The database system remains operational and accessible to clients at all times, even in the event of partial node or network partition failures.
  • Soft State: System state may fluctuate or drift over time even without client interaction, due to asynchronous replica propagation models.
  • Eventual Consistency: The system does not guarantee immediate consistency on every read, but guarantees that all replicas will eventually converge to identical states if no further updates occur.

Q186. Explain replication in MongoDB with reference to the primary and secondary members of a replica set, the election of a new primary when the current primary fails, and write concern. State the benefits of replication.

Unit V CO5 | Bloom L2 5 Marks End Term Score: 9.6

Replication in MongoDB provides redundancy, high availability, and automated failover across distributed nodes.

1. Replica Set Architecture:

  • Primary Member: Exactly one primary accepts all write operations, recording changes in a capped collection called the oplog (operations log).
  • Secondary Members: Secondaries continuously read the primary's oplog and apply operations asynchronously to replicate data state. They can serve read queries if configured.
  • Arbiter (Optional): A lightweight voting-only member that holds no data, used solely to break election ties in clusters with even node counts.

2. Election of a New Primary:

Members send heartbeat pings every 2 seconds. If secondaries receive no response from the primary within 10 seconds, an election is triggered. Secondaries nominate eligible members based on member priority and oplog recency; the node holding the most up-to-date oplog that wins a strict majority of votes becomes the new Primary.

3. Write Concern:

Write concern specifies the level of acknowledgement requested from MongoDB for write operations:

  • { w: 1 }: Acknowledged by Primary only (fast, but data could be lost if primary fails before replication).
  • { w: "majority" }: Acknowledged only after the write is committed to a majority of replica set nodes, preventing rollback during failover.
  • { j: true }: Ensures the operation is written to on-disk journal before returning acknowledgement.

4. Benefits of Replication:

Guarantees continuous 24/7 high availability, eliminates single points of failure, allows zero-downtime rolling maintenance/upgrades, and offloads heavy analytical read traffic from the primary node. Strong write concerns (such as w: 'majority') protect mission-critical applications against data rollbacks if a primary node suddenly experiences ungraceful hardware failure before replication completes.

In MongoDB replication, the Primary receives all writes and logs them in its oplog, while Secondaries copy the log. If the Primary goes down, nodes vote in a new Primary in seconds. Write Concern lets you choose between fast writes (acknowledged by primary only) or ultra-safe writes (acknowledged by a majority of servers). It guarantees 24/7 uptime without data loss.

Q188. Analyse the trade-offs of the CAP theorem for a distributed database during a network partition. Using this analysis, justify whether a CP or an AP design is more suitable for (i) an online banking ledger and (ii) a social-media news feed, and explain how sharding and replication help a NoSQL system to scale.

Unit V CO5 | Bloom L4 5 Marks End Term Score: 9.7

1. CAP Theorem Trade-Off Analysis during Network Partition:

The CAP theorem states that a distributed system cannot simultaneously guarantee Consistency ($C$), Availability ($A$), and Partition Tolerance ($P$). Because physical network partitions ($P$) (cable cuts, packet loss, hardware switch failures) are unavoidable in distributed architectures, systems must choose between Consistency or Availability when a partition occurs:

  • CP (Consistency + Partition Tolerance): Rejects the read/write request on the isolated partition to prevent stale or conflicting data, returning an error or timeout. Sacrifices Availability to preserve absolute mathematical correctness.
  • AP (Availability + Partition Tolerance): Returns the locally available value (even if stale) and accepts writes locally. Sacrifices immediate Consistency to guarantee 100% Availability.

2. Application Justifications:

  • (i) Online Banking Ledger: CP Design (e.g., Google Spanner, MongoDB with majority write concern).
    Justification: Financial ledgers require zero tolerance for dirty reads, phantom withdrawals, or double-spending. If a network partition prevents verifying account balances across branches, the system must abort the transaction rather than serve incorrect monetary balances.
  • (ii) Social-Media News Feed: AP Design (e.g., Apache Cassandra, Amazon DynamoDB).
    Justification: User experience demands seamless, uninterrupted availability. If a user sees a friend's post or like count 5 seconds late due to a network partition, the business impact is negligible compared to showing a broken error screen.

3. How Sharding and Replication Enable NoSQL Scaling:

  • Sharding (Horizontal Scale-Out): Splits massive collections into disjoint ranges based on a shard key, distributing storage and write throughput across dozens of commodity servers.
  • Replication (High Availability & Read Scaling): Maintains identical copies across nodes, eliminating single points of failure and distributing read query loads geographically.

When network wires snap, you must pick: CP locks down and throws an error to prevent wrong numbers (essential for banking where double-spending is illegal); AP keeps answering with slightly outdated posts (perfect for social media where staying online matters more than seeing a tweet 2 seconds late). Sharding splits data across disks to scale writes, while replication copies data to scale reads.
