Unit I: Intro & ER

DBMS
Definition

A Database Management System (DBMS) is software that interacts with end-users, applications, and the database itself to capture and analyze data. It allows users to create, read, update, and delete data in a database.

Advantages over File-Processing
  • Data Redundancy and Inconsistency: Centralizes data, eliminating duplicate files and ensuring updates propagate everywhere.
  • Data Isolation: Applications do not need to know the physical structure of the data files.
  • Integrity Problems: Allows defining explicit integrity constraints (e.g., account balance > 0).
  • Security Problems: Offers fine-grained access control and user authorization.
  • Concurrent Access: Manages simultaneous access securely, preventing anomalies.
Data redundancy and data inconsistency
Definitions
  • Data Redundancy: The unnecessary duplication of data in a database. (e.g., storing a student's address in both the Library and Department files).
  • Data Inconsistency: A consequence of redundancy where different copies of the same data hold different values (e.g., address updated in Library but not Department).
DBMS Solution

A DBMS minimizes redundancy by storing a single, centralized copy of the data (Data Normalization). Because there is only one authoritative copy, inconsistency is inherently prevented.

Give the difference between a database system and a file-based system
Differences
  • Structure: DB systems store data in structured formats (tables/graphs); File systems store data in plain text/binary files.
  • Data Independence: DB systems separate applications from data structure; File systems tightly couple applications to file formats.
  • Querying: DB systems provide robust query languages (SQL); File systems require custom application code to extract data.
Draw and explain the three-level (ANSI-SPARC) architecture of a DBMS
The Three Levels
  1. External Level (View Level): The highest level, describing only the part of the database relevant to a specific user group (hiding the rest).
  2. Conceptual Level (Logical Level): Describes what data is stored in the entire database and the relationships among those data. Used by DBAs.
  3. Internal Level (Physical Level): Describes exactly how the data is physically stored on disk (data structures, file organizations).
Exam Tip: The primary objective of this architecture is to achieve Data Independence.
Data abstraction
Definition

Data abstraction is the process of hiding complex internal data structures and storage details from the user, presenting only a simplified, usable view of the data.

Three Levels
  • Physical Level: Hides the complexity of block structures, indexing, and bytes on disk.
  • Logical Level: Hides physical storage but reveals entities, data types, and relationships. Developers interact here.
  • View Level: Hides the entire logical schema except for specific fields the end-user is authorized to see (e.g., a teller seeing only names and balances).
Terms schema and instance
Definition
  • Schema: The overall logical design/blueprint of the database. It changes rarely.
  • Instance: The snapshot of data residing in the database at a specific moment in time. It changes frequently.
Importance

This distinction is crucial for maintaining data independence—altering the schema (like adding a column) should not arbitrarily destroy the existing instances.

Data independence
Definition

Data independence is the ability to modify a schema definition in one level without affecting a schema definition in the next higher level.

Types
  • Physical Data Independence: Ability to modify the internal/physical schema without altering the conceptual schema. Example: Changing a file from sequential to a B+ tree index to improve performance; application code doesn't change.
  • Logical Data Independence: Ability to modify the conceptual schema without altering the external schema (user views). Example: Splitting an Employee table into two normalized tables; the original view can be maintained using a SQL JOIN, shielding the frontend application.
Who are the different types of database users
Types of Users
  • Parametric (Naive) Users: End-users who interact via standard GUI applications without knowing SQL (e.g., Bank Tellers).
  • Application Programmers: Software engineers who write the backend logic connecting to the DB.
  • Sophisticated Users: Analysts who interact directly with the DB using SQL queries to generate reports.
  • Database Administrators (DBA): IT professionals who manage security, schemas, and performance tuning.
List the responsibilities of a Database Administrator (DBA)
Responsibilities
  • Schema definition and modification.
  • Defining storage structures and access methods (indexing).
  • Granting user authority and managing access security.
  • Routine maintenance, database backups, and performance monitoring.
Hierarchical, network, relational and object-oriented data models
Comparison
  • Hierarchical: Data organized in a tree structure (1:N relationships). Fast but inflexible; requires navigating rigid pointers.
  • Network: Data organized in a graph (M:N relationships allowed). Highly complex and difficult to maintain.
  • Relational: Data organized in 2D tables (relations). Uses declarative SQL. Extremely flexible and mathematically sound.
  • Object-Oriented: Data stored as objects with methods, matching OOP languages. Best for complex data (e.g., CAD/CAM).
Most Widely Used

The Relational Model is most widely used today due to its simplicity, robust theoretical foundation (normalization), and standard interface (SQL) which provides unparalleled data independence.

Advantages of the relational model over the other data models
Advantages
  • Simplicity: Uses a simple tabular structure (rows and columns) that is easy to understand compared to complex graph/tree pointers.
  • Flexibility: Supports ad-hoc querying using standard SQL.
  • Data Independence: Strong separation between logical representation and physical storage.
Terms super key, candidate key, primary key and foreign key
Explanation
  • Super Key: Any combination of columns that uniquely identifies a row. (e.g., StudentID + Name)
  • Candidate Key: A minimal super key; it uniquely identifies a row with no unnecessary columns. (e.g., StudentID or Email)
  • Primary Key: The specific candidate key chosen to identify rows. Cannot be NULL. (e.g., StudentID)
  • Foreign Key: A column that refers to the primary key of another table, enforcing referential integrity. (e.g., Dept_ID in a Student table referencing the Department table)
Integrity constraints in a relational model
Definition

Integrity constraints are rules applied to a database to ensure the data is accurate, consistent, and valid.

The Four Constraints
  • Domain Constraint: Restricts the values a column can hold to a valid set (e.g., Age must be a positive integer).
  • Key Constraint: Ensures that candidate/primary keys are completely unique for every row.
  • Entity Integrity: States that no part of a Primary Key can be NULL, because a NULL value cannot uniquely identify a row.
  • Referential Integrity: States that if a foreign key exists in a relation, its value must either match a primary key value in the referenced relation or be NULL. (e.g., You cannot enroll a student in a non-existent Course_ID).
E-R model
Definition

The Entity-Relationship (E-R) model is a high-level conceptual data model that visually represents entities (objects) and the relationships between them.

Notations
  • Rectangle: Entity sets
  • Ellipse: Attributes
  • Diamond: Relationship sets
  • Lines: Link attributes to entities and entities to relationships
Entity, entity set, attribute and relationship, and illustrate each
Definitions
  • Entity: A real-world object with independent existence (e.g., a specific student).
  • Entity Set: A collection of similar entities (e.g., all Students).
  • Attribute: A property describing an entity (e.g., Name, Age).
  • Relationship: An association among two or more entities (e.g., Student Enroll Course).
Different types of attributes, simple, composite, derived, multivalued and key attribute,
Attribute Types
  • Simple: Indivisible atomic values (e.g., Gender).
  • Composite: Can be broken down into sub-parts (e.g., Name into First Name, Last Name).
  • Derived: Calculated from other attributes; not physically stored (e.g., Age derived from DOB).
  • Multivalued: Can hold multiple values for a single entity (e.g., Phone_Numbers).
  • Key: Uniquely identifies the entity (e.g., Roll_No).
Different types of relationships that can exist between two entities
Cardinality Ratios
  • One-to-One (1:1): One entity in A is associated with at most one in B. (e.g., Department 1:1 Manager).
  • One-to-Many (1:N): One entity in A is associated with many in B. (e.g., Department 1:N Employees).
  • Many-to-Many (M:N): Many entities in A associated with many in B. (e.g., Student M:N Course).
Weak entity set
Definition

A weak entity set lacks sufficient attributes to form a primary key. It depends on a strong entity (identifying owner) and uses the owner's key plus its own partial key to identify rows.

Example

A Dependent (spouse/child) of an Employee. The dependent is identified by combining their Name (partial key) with the owner's Employee ID.

Unary, binary and ternary relationships
Degrees of Relationships
  • Unary (Degree 1): Relationship between instances of a single entity set (e.g., Employee Manages Employee).
  • Binary (Degree 2): Relationship between two entity sets (e.g., Student Takes Course).
  • Ternary (Degree 3): Relationship connecting three entity sets simultaneously (e.g., Supplier Supplies Part To Project).
Exam Tip: A ternary relationship is not just three binary relationships; it represents a single fact involving all three entities together.
Total participation and partial participation constraints in an E-R diagram
Differentiation
  • Total Participation (Mandatory): Every entity MUST participate in at least one relationship. Indicated by a double line. (e.g., Every Employee must belong to a Department).
  • Partial Participation (Optional): Only some entities may participate. Indicated by a single line. (e.g., Only some Employees are Managers of a Department).
Generalization and specialization in the Extended E-R model
Specialization (Top-Down)

The process of defining a set of subclasses from a single entity type (the superclass). It involves identifying characteristics that distinguish some entities in the set from others.
Example: An Employee superclass can be specialized into Engineer, Manager, and Technician subclasses based on job role.

Generalization (Bottom-Up)

The reverse process of specialization. Multiple entity types with common attributes are synthesized into a single, generalized superclass.
Example: Car and Truck entities share attributes like Vehicle_ID and Price, so they can be generalized into a Vehicle superclass.

Overlapping and disjoint specialization
Disjoint Specialization

An entity can be a member of at most one subclass of the specialization. Denoted by a 'd' in the circle.
Example: An Employee can be either an Hourly_Employee or a Salaried_Employee, but never both at the same time.

Overlapping Specialization

An entity may be a member of more than one subclass of the specialization. Denoted by an 'o' in the circle.
Example: A Person can simultaneously be an Alumnus and an Employee of a university.

Aggregation in E-R modelling
Definition

Aggregation is an abstraction where a relationship set (and its associated entities) is treated as a higher-level entity set.

When is it required?

The basic E-R model cannot express relationships among relationships. Aggregation is required when a relationship between two entities needs to participate in another relationship with a third entity.

Example

Consider Employee working on a Project. This forms the relationship Works_On. If we want to record the Manager who oversees this specific (Employee-Project) assignment, we aggregate Works_On into a single entity, and create a new relationship Manages between it and Manager.

Mapping cardinality
Definition

Mapping cardinality (or cardinality ratio) expresses the number of entities to which another entity can be associated via a relationship set.

Types
  • One-to-One (1:1): An entity in A is associated with at most one entity in B, and vice versa.
  • One-to-Many (1:N): An entity in A is associated with any number of entities in B. An entity in B is associated with at most one entity in A.
  • Many-to-One (N:1): An entity in A is associated with at most one entity in B. An entity in B is associated with any number of entities in A.
  • Many-to-Many (M:N): An entity in A is associated with any number of entities in B, and vice versa.
Functional dependency
Definition

A functional dependency (FD) is a constraint between two sets of attributes in a relation. If A → B (A determines B), then for every valid instance of the relation, any two tuples that agree on the attribute A must also agree on the attribute B.

Importance

Functional dependencies are the theoretical bedrock of Normalization. They are used to specify constraints on data, discover candidate keys, and decompose relations to eliminate redundancy and update anomalies.

Insertion, deletion and update anomalies
The Three Anomalies
  • Update Anomaly: If data is stored redundantly, changing it in one row requires changing it in all rows. Missing one causes inconsistency (e.g., changing a department's location).
  • Insertion Anomaly: The inability to add data to the database due to absence of other data (e.g., unable to add a new Department because it has no Employees yet, and Employee_ID is the primary key).
  • Deletion Anomaly: The unintended loss of data when deleting a row (e.g., deleting the only employee in a department also deletes the department's information).
How Normalization Helps

Normalization resolves these by decomposing large, poorly structured tables into smaller, well-structured tables where each table represents a single logical theme or entity. By linking them with foreign keys, redundancy is eliminated, which inherently solves update, insertion, and deletion anomalies.

Normalization
Definition

Normalization is the process of organizing data to minimize redundancy and eliminate anomalies by dividing larger tables into smaller tables and defining relationships between them using functional dependencies.

The Normal Forms
  • First Normal Form (1NF): All attributes must be atomic (indivisible). No repeating groups or arrays allowed in a cell.
  • Second Normal Form (2NF): Must be in 1NF, and all non-key attributes must be fully functionally dependent on the entire primary key. (Eliminates partial dependencies).
  • Third Normal Form (3NF): Must be in 2NF, and no non-key attribute can be dependent on another non-key attribute. (Eliminates transitive dependencies: X → Y and Y → Z).
BCNF
Definition

Boyce-Codd Normal Form (BCNF) requires that for every non-trivial functional dependency X → Y, X must be a super key. It is a stronger, stricter version of 3NF.

Difference from 3NF

3NF allows a dependency X → Y where X is NOT a super key, provided that Y is a prime attribute (part of a candidate key). BCNF does not allow this exception. A table can be in 3NF but fail BCNF if it has overlapping candidate keys.

Example

Consider Relation(Student, Course, Instructor). Keys are (Student, Course) and (Student, Instructor). FD: Instructor → Course.
It is in 3NF because Course is a prime attribute. However, it violates BCNF because Instructor is not a super key.

Write a short note on 4NF and 5NF,
Fourth Normal Form (4NF)

Deals with Multi-valued Dependencies (MVD). A table is in 4NF if it is in BCNF and contains no non-trivial multi-valued dependencies (where one attribute determines a set of values for another, independent of a third).
Example: An Employee has multiple Skills and multiple Dependents. Storing them in one table creates massive redundancy. We split into (Emp, Skill) and (Emp, Dependent).

Fifth Normal Form (5NF)

Deals with Join Dependencies. Also known as Project-Join Normal Form (PJNF). A table is in 5NF if it is in 4NF and cannot be decomposed into smaller tables without losing data (lossless join). It ensures that all join dependencies are implied by candidate keys.

Lossless-join decomposition
Definition

Lossless-join decomposition means that if a relation R is decomposed into R1 and R2, joining them back together via a Natural Join will yield the exact original relation R, without any missing rows (loss of data) or extra spurious rows (creation of invalid data).

Condition

The decomposition is lossless if the common attribute(s) between R1 and R2 form a super key for either R1 or R2. (i.e., R1 ∩ R2 → R1 OR R1 ∩ R2 → R2).

Example

Splitting Employee(ID, Name, Dept, Dept_Location) into Emp(ID, Name, Dept) and Department(Dept, Dept_Location) is lossless because their intersection, Dept, is a primary key for the Department table.

Dependency-preserving decomposition and give a suitable example
Definition

A decomposition is dependency-preserving if the union of the functional dependencies in the decomposed relations logically implies all the functional dependencies of the original relation. This ensures that updates can be checked for validity without joining the tables back together.

Example

Original Relation: R(A, B, C)
Functional Dependencies (FDs): A → B, B → C
Decomposition: R1(A, B) and R2(B, C).
FDs in R1: A → B.
FDs in R2: B → C.
Since (A → B) ∪ (B → C) covers all original FDs, it is a dependency-preserving decomposition.

Consider an unnormalized relation Student_Marks(Rollno, Name, Subject, Marks) where a student appears in multiple rows, one per subject
Functional Dependencies (FDs)

Assumed FDs based on logic:

  1. FD1: Rollno → Name (A student has one name)
  2. FD2: Rollno, Subject → Marks (A specific student's marks in a specific subject)

The primary key for the unnormalized relation is (Rollno, Subject).

Step 1: 1NF to 2NF

In the original relation, Name depends ONLY on Rollno, which is a part of the primary key. This is a Partial Dependency. We decompose to eliminate it:

  • Student(Rollno, Name)
  • Performance(Rollno, Subject, Marks)
Step 2: 2NF to 3NF

In the new tables, there are no non-key attributes depending on other non-key attributes (no transitive dependencies). Therefore, the tables are already in 3NF.

Violation of 3NF

Consider Employee(EmpID, Name, DeptID, DeptName) where EmpID is the primary key.

Functional Dependencies:
1. EmpID → DeptID
2. DeptID → DeptName
Because EmpID → DeptName through DeptID, this is a Transitive Dependency. 3NF forbids non-prime attributes depending on other non-prime attributes.

Decomposition into 3NF

We decompose the relation to separate the department details:

  1. Employee(EmpID, Name, DeptID)
  2. Department(DeptID, DeptName)
In the table below, each mentor teaches only one subject
Checking BCNF

Relation: R(StudentID, Subject, Mentor)
FDs: {StudentID, Subject} → Mentor, and Mentor → Subject (each mentor teaches one subject).
Because Mentor → Subject exists, but Mentor is not a super key, the table violates BCNF (even though it is in 3NF since Subject is a prime attribute).

BCNF Decomposition

We must pull the violating determinant out into its own table:

  1. Mentor_Subject(Mentor, Subject)
  2. Student_Mentor(StudentID, Mentor)

Now all determinants are candidate keys.

Table below stores a student's hobbies and the languages they know together, forcing every combination to be listed
Violation of 4NF

Relation: R(StudentID, Hobby, Language)
A student's hobbies are completely independent of the languages they speak. This creates two Multi-Valued Dependencies (MVDs):
StudentID ⟶ Hobby and StudentID ⟶ Language.
Storing them together forces a Cartesian product (e.g., 2 hobbies × 3 languages = 6 rows for one student). Since 4NF forbids non-trivial MVDs, this violates 4NF.

4NF Decomposition

Split into two tables to eliminate the Cartesian product:

  1. Student_Hobby(StudentID, Hobby)
  2. Student_Language(StudentID, Language)
Given a relation R(A, B, C, D, E)
Computing {A, C}+
  1. Start with the base set: {A, C}
  2. Using A → B, add B. The set becomes {A, B, C}
  3. Using BC → D (we have both B and C), add D. The set becomes {A, B, C, D}
  4. Using D → E, add E. The set becomes {A, B, C, D, E}
Conclusion

Since the closure of {A, C} contains all the attributes of the relation R, {A, C} is a super key. Assuming no proper subset of {A, C} can determine all attributes, {A, C} is a Candidate Key.

Consider the relation Student_Course(Roll_No, Course_ID, Course_Name, Instructor)
Analysis

Primary Key: (Roll_No, Course_ID)
The FD Course_ID → Course_Name is a Partial Dependency because Course_Name depends only on a part of the primary key (Course_ID), violating 2NF.

2NF Decomposition
  1. Course(Course_ID, Course_Name)
  2. Student_Course(Roll_No, Course_ID, Instructor)

Now, both relations are in 2NF.

Consider the relation Employee(Emp_ID, Emp_Name, Dept_ID, Dept_Name, Dept_Location)
Analysis

Primary Key: Emp_ID. Since the key is a single attribute, there are no partial dependencies, so it is in 2NF.
However, the FD Dept_ID → Dept_Name, Dept_Location creates a Transitive Dependency (Emp_ID → Dept_ID → Dept_Name). This violates 3NF.

3NF Decomposition
  1. Employee(Emp_ID, Emp_Name, Dept_ID)
  2. Department(Dept_ID, Dept_Name, Dept_Location)
Consider the relation R(Student, Subject, Teacher)
Analysis

Candidate Keys: (Student, Subject) and (Student, Teacher).
For the FD Teacher → Subject, Teacher is a determinant but not a super key. Therefore, R violates BCNF.

BCNF Decomposition
  1. Teach_Subj(Teacher, Subject)
  2. Stud_Teach(Student, Teacher)

Both tables are now strictly in BCNF.

Given a relation R(A, B, C, D)
Candidate Keys
  • {A, B}+ = {A, B, C, D}
  • {B, C}+ = {A, B, C, D} (since C → D and D → A)
  • {B, D}+ = {A, B, C, D} (since D → A and AB → C)

The candidate keys are AB, BC, and BD. All attributes are prime attributes except none (every attribute is part of at least one candidate key).

Highest Normal Form

Because there are no non-prime attributes, the relation is automatically in 3NF.
However, check BCNF: The FD C → D has determinant C, which is not a super key. Thus, it violates BCNF. The highest normal form is 3NF.

Generalization, specialization and aggregation in the Extended E-R model
Specialization (Top-Down)

The process of defining a set of subclasses from an entity type based on distinguishing characteristics.
Example: An Employee can be specialized into Hourly_Emp and Salaried_Emp.

Generalization (Bottom-Up)

The reverse of specialization. Extracting shared characteristics from multiple entity types to create a generalized superclass.
Example: Car and Truck generalized into Vehicle.

Aggregation

Treating a relationship between entities as a single abstract entity, allowing relationships to participate in other relationships.
Example: A Project and Employee have a Works_On relationship. A Manager manages the entire Works_On relationship, treating it as one aggregated entity.

Decomposition

Decomposition is the process of breaking down a large, poorly-designed relation into two or more smaller relations to eliminate redundancy and anomalies.

Lossless-Join Decomposition

A decomposition of R into R1 and R2 is lossless if joining R1 and R2 back together using a Natural Join yields the exact original relation R, without generating spurious (fake) tuples.

Condition: The common attributes must be a candidate key for at least one of the decomposed relations (i.e., R1 ∩ R2 → R1 or R1 ∩ R2 → R2).

Dependency-Preserving Decomposition

A decomposition is dependency-preserving if all original functional dependencies can be checked and enforced using only the decomposed relations, without needing to join them back together.

How is decomposition related to normalization

Normalization uses Decomposition as its primary mechanism. When a relation violates a normal form, we decompose it into smaller relations that satisfy the normal form.

Example

Suppose a relation R(EmpID, EmpName, DeptID, DeptName) where EmpID → EmpName, DeptID and DeptID → DeptName.

  • This violates 3NF due to the transitive dependency (EmpID → DeptID → DeptName).
  • Normalization Process: We decompose R into two relations to remove the redundancy:
    1. Employee(EmpID, EmpName, DeptID)
    2. Department(DeptID, DeptName)

This decomposition is both lossless-join (because DeptID is a primary key in Department) and dependency-preserving.

Transaction

A transaction is a logical unit of work consisting of one or more SQL statements that must be executed entirely or not at all.

ACID Properties (Bank Transfer Example: A to B):

  • Atomicity: "All or nothing." If money is deducted from A, it MUST be credited to B. If either fails, the entire transaction is rolled back.
  • Consistency: The database must remain in a valid state. The total sum of A + B's balances must be the same before and after the transaction.
  • Isolation: Concurrent transactions do not interfere with each other. If another transaction reads A's balance during the transfer, it will see the state either strictly before or strictly after, not midway.
  • Durability: Once the transaction is committed, the changes are permanent and will survive system crashes.

Transaction State Diagram

COMMIT, ROLLBACK and SAVEPOINT
  • COMMIT: Saves all changes made during the current transaction permanently.
  • ROLLBACK: Undoes all changes made during the current transaction, reverting to the last commit.
  • SAVEPOINT: Sets a marker within a transaction so you can roll back to that specific point without canceling the entire transaction.
START TRANSACTION;
UPDATE ACCOUNT SET Balance = Balance - 500 WHERE Acc_No = 'A101';
SAVEPOINT step1;
UPDATE ACCOUNT SET Balance = Balance + 500 WHERE Acc_No = 'A102';
-- If something goes wrong here:
ROLLBACK TO step1; -- Undoes only the A102 update
COMMIT; -- Saves the final state

In one or two lines each, state the purpose of a stored procedure, a sequence (AUTO_INCREMENT in MySQL), a cursor and a trigger
  • Stored Procedure: A pre-compiled collection of SQL statements saved in the database that can be executed as a single callable routine.
  • Sequence (AUTO_INCREMENT): Automatically generates unique, sequential numeric values, typically used for primary keys.
  • Cursor: A database object used to retrieve and process rows one by one from a result set inside a stored procedure.
  • Trigger: A special type of stored procedure that automatically executes (fires) in response to specific DML events (INSERT, UPDATE, DELETE) on a table.
BEFORE trigger and an AFTER trigger

BEFORE Trigger executes before the triggering DML operation is applied (useful for validation/modification of incoming data). AFTER Trigger executes after the operation (useful for auditing or cascading changes to other tables).

NEW refers to the incoming data (being inserted or updated). OLD refers to the existing data in the table before the operation (being updated or deleted).

Purpose of exception handling in a stored procedure

Exception handling ensures that if an error occurs during execution, the stored procedure can catch it and gracefully handle it (e.g., rolling back a transaction) instead of crashing.

  • DECLARE ... HANDLER: Defines a block of code to execute when a specific error or condition occurs (e.g., DECLARE CONTINUE HANDLER FOR SQLEXCEPTION).
  • SIGNAL: Used to artificially raise a custom error or exception, returning a custom SQLSTATE and message to the caller.
