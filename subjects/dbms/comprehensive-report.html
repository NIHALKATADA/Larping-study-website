Unit I: Introduction, ER Modeling, and Normalization

Introduction to DBMS & Architecture

  • DBMS vs File System: DBMS reduces data redundancy, inconsistency, and provides better security, concurrent access, and crash recovery compared to file processing.
  • Data Abstraction: Hides complexity. Levels: Physical (how data is stored), Logical (what data is stored), View (what users see).
  • ANSI-SPARC Architecture: Internal, Conceptual, and External schemas ensuring Data Independence.
  • Schema vs Instance: Schema is the structure (static), Instance is the data at a specific moment (dynamic).
  • Data Independence: Ability to modify schema at one level without changing the next. Logical: conceptual -> external. Physical: internal -> conceptual.
  • Users & DBA: Naive users, application programmers, sophisticated users, DBAs. DBA tasks: schema definition, access control, backup/recovery.
  • Data Models: Relational is most popular due to mathematical foundation and simplicity compared to Hierarchical, Network, and Object-Oriented.
Don't confuse Data Abstraction with Data Independence. Abstraction hides details; Independence means changing schema doesn't break applications.
Moving forward from Introduction to DBMS & Architecture, let's break down the mechanics of Relational Model & Integrity Constraints.

Relational Model & Integrity Constraints

  • Keys: Super key (uniquely identifies row), Candidate key (minimal super key), Primary key (chosen candidate key), Foreign key (references PK in another table).
  • Integrity Constraints: Domain (valid types/values), Key (uniqueness), Entity (PK not null), Referential (FK must match PK or be null).
Example: In Employee(EmpID, DeptID), DeptID is a Foreign Key referencing Department(DeptID).
While Relational Model & Integrity Constraints gives us the theoretical background, Entity-Relationship (E-R) Model provides the next layer of complexity.

Entity-Relationship (E-R) Model

  • Basic Notations: Entity (Rectangle), Attribute (Oval), Relationship (Diamond).
  • Attributes: Simple, Composite (divisible, e.g., Address), Derived (calculated, e.g., Age from DOB), Multivalued (double oval), Key (underlined).
  • Relationships: Unary, Binary, Ternary based on degree. Mapping Cardinalities: 1:1, 1:N, N:1, M:N.
  • Weak Entity: Doesn't have its own primary key, depends on strong entity (double rectangle).
  • Participation: Total (double line, every entity participates) vs Partial.
  • Extended ER: Generalization (bottom-up), Specialization (top-down, overlapping/disjoint), Aggregation (relationship treated as entity).
Always clearly mark cardinalities (1, N) and use double lines for total participation in E-R diagram problems!
Now that we have a solid grasp of Entity-Relationship (E-R) Model, the natural next step is to explore Normalization & Functional Dependencies.

Normalization & Functional Dependencies

  • Functional Dependency (FD): X -> Y means X uniquely determines Y.
  • Anomalies: Insertion, Deletion, Update anomalies occur in unnormalized tables.
  • Normal Forms:
    • 1NF: Atomic values only.
    • 2NF: 1NF + no partial dependencies (non-prime attribute depends on whole candidate key).
    • 3NF: 2NF + no transitive dependencies (non-prime depends only on candidate keys).
    • BCNF: Stricter 3NF. For every X -> Y, X must be a super key.
    • 4NF/5NF: Deal with multivalued dependencies and join dependencies.
  • Decomposition: Must be Lossless-Join (no spurious tuples on natural join) and Dependency-Preserving (all FDs can be checked).
A relation is in BCNF but not 3NF if there's a prime attribute functionally dependent on a non-prime attribute. This violates BCNF but is allowed in 3NF!
Moving forward from Normalization & Functional Dependencies, let's break down the mechanics of Problem Solving: E-R Diagrams and Normalization.

Problem Solving: E-R Diagrams and Normalization

  • E-R Design: Common scenarios like University, Online Bookstore, Hospital, Bank, Company. Identify main entities, relationships, attributes, and cardinality.
  • Normalization Exercises: Find candidate keys using FD closure. Identify highest normal form. Decompose by placing violating FDs in new tables while preserving keys.
Example: Given R(A,B,C,D,E) with {A->B, BC->D, D->E}. Closure of {A,C}+ = {A,C,B,D,E}. So {A,C} is a candidate key.

Unit II: Relational Algebra, SQL, and Query Processing

Relational Algebra & Calculus

  • RDBMS vs DBMS: RDBMS enforces relational model (tables) and integrity constraints, DBMS is generic.
  • Relational Algebra: Procedural language. Basic ops: Select, Project, Union, Set Difference, Cartesian Product, Rename.
  • Derived Ops: Join, Intersection, Division (useful for "every" queries).
  • Relational Calculus: Non-procedural (what to get, not how). Tuple Relational Calculus (TRC) & Domain Relational Calculus (DRC).
  • Degree & Cardinality: Degree = number of columns, Cardinality = number of rows.
Example: Division: Find students enrolled in ALL courses. Students / Courses.
With Relational Algebra & Calculus in mind, we can see why SQL Basics: DDL, DML, DCL, TCL becomes crucial in this context.

SQL Basics: DDL, DML, DCL, TCL

  • DDL: CREATE (make table), ALTER (modify structure), DROP (delete table/data), TRUNCATE (fast delete all rows).
  • DML: INSERT, UPDATE, DELETE (remove rows conditionally), SELECT (retrieve).
  • DCL: GRANT (give permissions), REVOKE (remove permissions).
  • TCL: COMMIT (save permanently), ROLLBACK (undo changes), SAVEPOINT (partial rollback point).
TRUNCATE is DDL, cannot be rolled back in many DBMS, and is faster than DELETE.
Moving forward from SQL Basics: DDL, DML, DCL, TCL, let's break down the mechanics of SQL Joins & Subqueries.

SQL Joins & Subqueries

  • Joins: Inner (matches only), Left Outer (all left + matches), Right Outer, Full Outer.
  • Equi vs Natural Join: Equi uses '=' on specific columns; Natural implicitly joins on ALL columns with same name and drops duplicates.
  • Self/Cross Join: Self joins table to itself; Cross join is Cartesian product.
  • Subqueries: Nested query inside WHERE/HAVING. Uses IN, EXISTS, ANY, ALL.
  • Correlated Subquery: Inner query references outer query; executes once for each outer row.
Correlated subqueries are slower because the inner query runs iteratively for every row of the outer query.
Having established the core principles of SQL Joins & Subqueries, we now turn our attention to Aggregation & Views.

Aggregation & Views

  • Aggregate Functions: COUNT, SUM, AVG, MAX, MIN.
  • GROUP BY & HAVING: GROUP BY groups rows; HAVING filters groups (unlike WHERE which filters rows).
  • ORDER BY: Sorts result set (ASC/DESC).
  • Views: Virtual tables based on queries. Simple views (one table, updatable) vs Complex/Materialized views (joins, aggregates, read-only/stored physically).
WHERE happens BEFORE grouping, HAVING happens AFTER grouping.

Unit III: Advanced SQL, Constraints, and Transactions

Advanced DDL & Constraints

  • Auto-commit: DDL statements auto-commit transactions in most DBMS (cannot be rolled back).
  • Constraints: NOT NULL, UNIQUE (allows nulls but distinct), PRIMARY KEY (NOT NULL + UNIQUE), FOREIGN KEY, CHECK (validates condition).
  • Table vs Column level: Column-level defined inline; Table-level defined at end (mandatory for composite keys).
  • Table operations: CREATE TABLE ... AS SELECT (backup), ALTER TABLE add/modify/drop columns or constraints, Rename tables.
Example: ALTER TABLE Employee ADD CONSTRAINT fk_dept FOREIGN KEY(Dept_ID) REFERENCES Department(Dept_ID);
Building on our understanding of Advanced DDL & Constraints, let's dive into SQL Built-in Functions.

SQL Built-in Functions

  • Numeric: ROUND(78.3456, 2)=78.35, TRUNCATE(78.3456, 2)=78.34. CEIL, FLOOR, ABS, MOD, POWER, SQRT.
  • Date: CURDATE(), DATEDIFF(date1, date2), DATE_ADD/SUB, DATE_FORMAT.
  • String: CONCAT(str1, str2), UPPER/LOWER, LENGTH, SUBSTRING(str, pos, len), TRIM, REPLACE.
ROUND rounds to nearest value, TRUNCATE just chops off the digits without rounding.
With SQL Built-in Functions in mind, we can see why Set Operations & Advanced Constructs becomes crucial in this context.

Set Operations & Advanced Constructs

  • Set Operators: UNION (removes duplicates), UNION ALL (keeps duplicates), INTERSECT, MINUS/EXCEPT. Rule: Queries must have same number of columns & compatible data types.
  • CASE & IF: Used for conditional logic in SELECT.
  • COALESCE: Returns first non-null value in a list. Useful for default values.
Example: SELECT COALESCE(Nominee_Name, 'Not Registered') FROM Accounts;
Moving forward from Set Operations & Advanced Constructs, let's break down the mechanics of Transactions & Programmability.

Transactions & Programmability

  • Transactions (ACID): Atomicity (all or nothing), Consistency (valid state), Isolation (concurrent safe), Durability (permanent).
  • Programmability:
    • Stored Procedure: Precompiled SQL code block.
    • Sequence/AUTO_INCREMENT: Generates sequential numbers.
    • Cursor: Iterates through query result row-by-row.
    • Trigger: Code that runs automatically BEFORE/AFTER an INSERT/UPDATE/DELETE. NEW refers to incoming row, OLD refers to existing/deleted row.
  • Exception Handling: DECLARE ... HANDLER catches errors; SIGNAL raises custom errors.
Use BEFORE triggers for data validation/modification, and AFTER triggers for auditing/logging changes.
