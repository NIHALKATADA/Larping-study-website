Unit I: Introduction to DBMS, E-R Modeling, and Normalization

Introduction to DBMS

A Database Management System (DBMS) is a software system designed to store, retrieve, and manage data efficiently and securely. It serves as an interface between the user and the database, ensuring that data is consistently organized and easily accessible.

Example: MySQL, PostgreSQL, Oracle, and Microsoft SQL Server are popular DBMS software.
With Introduction to DBMS in mind, we can see why DBMS vs File System becomes crucial in this context.

DBMS vs File System

Before DBMS, data was stored in traditional file-processing systems (like flat files or CSVs). This led to issues like data redundancy (duplication of data) and data inconsistency (different copies having different values).

FeatureDBMSFile-Based System
Data RedundancyMinimal redundancy due to normalization.High redundancy as files are isolated.
Data ConsistencyHigh consistency. Updates reflect everywhere.Inconsistent if multiple copies exist.
Data AccessProvides query languages (e.g., SQL) for easy access.Requires writing custom application programs.
SecurityHigh security with user access controls.Very little security mechanism.
To fully appreciate Three-Level ANSI-SPARC Architecture, we must apply what we just learned about DBMS vs File System.

Three-Level ANSI-SPARC Architecture

The DBMS architecture is divided into three levels to separate the user applications from the physical database:

  • Internal/Physical Level: Describes how the data is actually stored on the storage devices.
  • Conceptual/Logical Level: Describes what data is stored and the relationships between them.
  • External/View Level: Describes only a part of the entire database that a specific user needs to see.
Exam Trap: Don't confuse logical data independence with physical data independence. Physical data independence is the ability to modify the internal schema without altering the conceptual schema. Logical data independence is the ability to modify the conceptual schema without altering the external schemas.
Transitioning from Three-Level ANSI-SPARC Architecture, we now examine Schema and Instance, which builds upon these foundational rules.

Schema and Instance

A Schema is the overall design or structure of the database (rarely changes). An Instance is the actual data stored in the database at a particular moment in time (changes frequently).

With Schema and Instance in mind, we can see why Database Users and DBA becomes crucial in this context.

Database Users and DBA

Database systems are used by various classes of users:

  • Naive Users: Interact with the system by invoking one of the application programs (e.g., banking clerks).
  • Application Programmers: Computer professionals who write application programs.
  • Sophisticated Users: Interact without writing programs, typically using query languages (e.g., Data Analysts).
  • Database Administrator (DBA): The central authority managing the database.
Pro-Tip: The DBA is responsible for schema definition, storage structure and access-method definition, granting authorizations, and routine maintenance (backups).
To fully appreciate Data Models, we must apply what we just learned about Database Users and DBA.

A data model is a collection of conceptual tools for describing data, data relationships, data semantics, and consistency constraints.

With Data Models in mind, we can see why Relational Model & Keys becomes crucial in this context.

Relational Model & Keys

The relational model represents data as a collection of tables (relations).

  • Super Key: A set of one or more attributes that uniquely identifies a row.
  • Candidate Key: A minimal super key.
  • Primary Key: A candidate key chosen by the database designer as the principal means of identifying rows.
  • Foreign Key: An attribute in one table that refers to the primary key in another table.
Example: In a Student table, (RollNo, Email) is a super key. RollNo is a candidate key and could be chosen as the Primary Key.
Having established the core principles of Relational Model & Keys, we now turn our attention to Integrity Constraints.

Integrity Constraints

Integrity constraints ensure data accuracy and consistency.

  • Domain Integrity: Ensures columns contain valid values (e.g., Age > 0).
  • Entity Integrity: Ensures the Primary Key is not NULL.
  • Referential Integrity: Ensures a Foreign Key value must match a valid Primary Key value in the referenced table.
Transitioning from Integrity Constraints, we now examine E-R Modeling, which builds upon these foundational rules.

E-R Modeling

The Entity-Relationship (E-R) Model is a conceptual data model that views the real world as a set of basic objects (entities) and relationships among them.

  • Entity: A "thing" or "object" in the real world (e.g., Student).
  • Attribute: Properties of an entity (e.g., Name, Age).
  • Relationship: An association among several entities.
Having established the core principles of E-R Modeling, we now turn our attention to Types of Attributes.

Types of Attributes

  • Simple vs Composite: Simple cannot be divided (e.g., Age), Composite can be divided (e.g., Name -> First, Last).
  • Single-valued vs Multivalued: Multivalued can have multiple values (e.g., Phone Numbers).
  • Derived: Value can be calculated from other attributes (e.g., Age derived from Date of Birth).
Now that we have a solid grasp of Types of Attributes, the natural next step is to explore Generalization, Specialization, and Aggregation.

Generalization, Specialization, and Aggregation

Generalization is a bottom-up approach combining lower-level entities into a higher-level entity. Specialization is top-down, breaking an entity into sub-entities. Aggregation treats a relationship as an entity itself to associate it with other entities.

Building on our understanding of Generalization, Specialization, and Aggregation, let's dive into Normalization.

Normalization

Normalization is the process of organizing data to minimize redundancy and eliminate insertion, update, and deletion anomalies.

  • 1NF (First Normal Form): Domain of each attribute contains only atomic (indivisible) values.
  • 2NF (Second Normal Form): In 1NF and no partial dependencies (non-prime attributes must depend on the FULL primary key).
  • 3NF (Third Normal Form): In 2NF and no transitive dependencies (non-prime attributes must not depend on other non-prime attributes).
  • BCNF (Boyce-Codd Normal Form): A stricter version of 3NF. For every functional dependency X -> Y, X must be a super key.
Exam Trap: Remember that BCNF is stricter than 3NF. A relation in BCNF is always in 3NF, but a relation in 3NF might not be in BCNF.

Unit II: Relational Algebra & SQL

Relational Algebra

Relational Algebra is a procedural query language. It consists of a set of operations that take one or two relations as input and produce a new relation as their result.

Derived operations include Join, Intersection, and Division.

Example: Division is useful for queries like "Find students who have taken ALL courses."
FeatureRelational AlgebraRelational Calculus
NatureProcedural (How to get data).Declarative (What data to get).
ComplexityEasier to construct step-by-step.Uses logical predicates.
Having established the core principles of Relational Algebra, we now turn our attention to Introduction to SQL.

Introduction to SQL

SQL (Structured Query Language) is the standard language for relational databases. It consists of several sub-languages:

  • DDL (Data Definition Language): CREATE, ALTER, DROP, TRUNCATE.
  • DML (Data Manipulation Language): INSERT, UPDATE, DELETE, SELECT.
  • DCL (Data Control Language): GRANT, REVOKE.
  • TCL (Transaction Control Language): COMMIT, ROLLBACK, SAVEPOINT.
Moving forward from Introduction to SQL, let's break down the mechanics of SQL Queries and Joins.

SQL Queries and Joins

Joins combine rows from two or more tables based on a related column between them.

Join TypeDescription
Inner JoinReturns records that have matching values in both tables.
Left Outer JoinReturns all records from the left table, and matched records from the right table.
Right Outer JoinReturns all records from the right table, and matched records from the left table.
Full Outer JoinReturns all records when there is a match in either left or right table.
Building on our understanding of SQL Queries and Joins, let's dive into GROUP BY and HAVING.

GROUP BY and HAVING

The GROUP BY statement groups rows that have the same values into summary rows. The HAVING clause was added to SQL because the WHERE keyword cannot be used with aggregate functions.

Pro-Tip: WHERE filters rows before grouping, whereas HAVING filters groups after grouping.
Transitioning from GROUP BY and HAVING, we now examine Views, which builds upon these foundational rules.

Views

A View is a virtual table based on the result-set of an SQL statement. It simplifies complex queries and enhances security by restricting access to underlying tables.

Unit III: Advanced SQL & Transaction Management

Table Creation & Constraints

SQL constraints are used to specify rules for the data in a table.

  • NOT NULL: Ensures that a column cannot have a NULL value.
  • UNIQUE: Ensures that all values in a column are different.
  • PRIMARY KEY: A combination of a NOT NULL and UNIQUE. Uniquely identifies each row.
  • FOREIGN KEY: Prevents actions that would destroy links between tables.
  • CHECK: Ensures that the values in a column satisfy a specific condition.
Example: A table can have multiple UNIQUE constraints (e.g., Email, Phone), but only ONE PRIMARY KEY to uniquely identify the row fundamentally.
Building on our understanding of Table Creation & Constraints, let's dive into SQL Functions.

SQL Functions

Functions in SQL provide powerful ways to manipulate strings, numbers, and dates.

Now that we have a solid grasp of SQL Functions, the natural next step is to explore Numeric Functions.

Numeric Functions

ROUND rounds a number to a specified number of decimal places, while TRUNCATE simply chops off the decimals without rounding.

Moving forward from Numeric Functions, let's break down the mechanics of Date Functions.

Date Functions

DATEDIFF returns the number of days between two dates. DATE_ADD adds a time/date interval to a date.

Having established the core principles of Date Functions, we now turn our attention to Set Operations.

Set Operations

Set operators combine the results of two or more query blocks into a single result.

Pro-Tip: Both SELECT statements must have the same number of columns in the result sets with similar data types.
To fully appreciate Transaction Management, we must apply what we just learned about Set Operations.

Transaction Management

A Transaction is a logical unit of work that contains one or more SQL statements.

Transactions must follow the ACID properties:

  • Atomicity: "All or nothing" rule. Either all operations execute or none.
  • Consistency: Ensures the database moves from one consistent state to another.
  • Isolation: Concurrent transactions execute independently of one another.
  • Durability: Once a transaction is committed, changes are permanent, even after a system failure.
Example: In a bank transfer, deducting money from Account A and adding to Account B must be Atomic. If the system crashes after deduction but before addition, the transaction rolls back.
To fully appreciate Advanced Constructs, we must apply what we just learned about Transaction Management.

Advanced Constructs

Advanced constructs like CASE, COALESCE, and Stored Procedures provide programming capabilities within SQL.

  • CASE: Returns a value when the first condition is met (like an IF-THEN-ELSE statement).
  • COALESCE: Returns the first non-null value in a list.
  • Stored Procedure: Prepared SQL code that you can save, so the code can be reused over and over again.
  • Trigger: SQL code that automatically executes in response to certain events on a particular table.
