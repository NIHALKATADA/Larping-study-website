Unit I: Introduction to DBMS CO1

Architecture & Data Independence U1

The 3-schema architecture separates user views (External), logic (Conceptual), and storage (Internal). It ensures data independence, allowing changes in one schema without affecting others.

Example: Changing file structure from sequential to B+ tree (Physical Independence) doesn't alter SQL queries at the Conceptual level.
Pro-Tip: Logical data independence is much harder to achieve than physical, as application logic tightly binds to the conceptual schema.

Keys & Constraints U1

Super keys identify tuples uniquely. Candidate keys are minimal super keys. Primary keys are chosen candidate keys. Foreign keys enforce referential integrity between tables.

Example: `{EmpID, Email}` is a Super Key. `EmpID` is a Candidate and Primary Key.
Exam Trap: A relation can have multiple candidate keys but strictly ONE primary key. Nulls are not allowed in PKs (Entity Integrity).

Normalization: 1NF to BCNF U1

1NF mandates atomic domains. 2NF removes partial dependencies (non-prime depends on part of PK). 3NF eliminates transitive dependencies. BCNF strictly enforces every determinant as a candidate key.

Example: If `City -> Zip` and `Zip -> State`, `City -> State` is a transitive dependency violating 3NF.
Exam Trap: BCNF decomposition may result in the loss of functional dependency preservation, unlike 3NF which guarantees both lossless join and dependency preservation.

Deep Dive: ER to Relational Mapping U1

erDiagram EMPLOYEE ||--o{ DEPENDENT : "has (weak)" EMPLOYEE { string EmpID PK } DEPENDENT { string DepName PK "Partial" }

Strong entities map directly to tables. Weak entities map to tables using a composite key: their own partial key + the strong entity's primary key. M:N relationships require a separate junction table.

Example: The DEPENDENT table uses `(EmpID, DepName)` as its primary key.
Pro-Tip: In total participation, foreign key constraints often use `ON DELETE CASCADE` to maintain consistency.

Normalization Applied Example Applied Concept

Given: R(Student, Subject, Teacher, Mentor) with FDs: Student → Mentor, Mentor → Subject, Subject → Teacher.

Check 3NF: Student → Mentor is fine (Student is a candidate key). But Mentor → Subject has a non-prime determinant (Mentor) that is not a superkey, violating 3NF.

Decomposition into 3NF:

  • R1(Mentor, Subject) — from Mentor → Subject
  • R2(Subject, Teacher) — from Subject → Teacher
  • R3(Student, Mentor) — from Student → Mentor (preserves candidate key)

Unit II: Relational Database Concepts CO2

Relational Algebra Core U2

A procedural query language defining execution steps. Core operators include Selection (σ, row filter), Projection (π, column filter), Cartesian Product (×), Set Difference (-), and Union (∪).

Example: `π_name(σ_age>20(Student))` filters students older than 20, projecting only their names.
Exam Trap: Union compatibility requires relations to have identical degree (number of attributes) and compatible domains.

Advanced Relational Algebra U2

Derived operators simplify queries: Natural Join (⋈) implicitly matches common attributes, and Division (÷) identifies universal quantification scenarios (e.g., "all").

Example: `Students ÷ Courses` returns students who have enrolled in EVERY available course.
Pro-Tip: The Division operator is technically derived using Projection, Set Difference, and Cartesian Product.

Tuple vs Domain Relational Calculus U2

Calculus is non-procedural (describes WHAT to fetch, not HOW). TRC evaluates on a per-tuple basis. DRC evaluates attributes using domain variables.

Example (TRC): `{t | t ∈ Student ∧ t.age > 20}`.
Exam Trap: Unsafe queries (like infinite sets `{t | ¬(t ∈ Student)}`) are possible in calculus but syntactically disallowed in safe TRC systems.

Unit III: Structured Query Language (SQL) CO3

SQL Execution Pipeline U3

flowchart LR F[FROM] --> W[WHERE] --> G[GROUP BY] --> H[HAVING] --> S[SELECT] --> O[ORDER BY]

Understanding logical execution order prevents semantic errors. `WHERE` filters rows prior to aggregation, while `HAVING` filters aggregated buckets.

Example: You cannot use a column alias defined in `SELECT` inside the `WHERE` clause, because `WHERE` executes first.
Pro-Tip: This is why `COUNT(*)` in `WHERE` throws an error; aggregation hasn't happened yet!

Correlated Subqueries U3

An inner query that references columns from the outer query. It executes row-by-row iteratively for each tuple processed by the outer query, degrading performance.

Example: `SELECT * FROM Emp e1 WHERE Salary > (SELECT AVG(Salary) FROM Emp e2 WHERE e1.Dept = e2.Dept)`
Exam Trap: Contrast with non-correlated subqueries which execute exactly once. Use `EXISTS` instead of `IN` for correlated lookups to short-circuit execution.

Triggers & Views U3

Views are virtual tables providing logical independence. Triggers execute procedural code in response to DML events (INSERT/UPDATE/DELETE), typically enforcing complex business rules.

Example: `CREATE TRIGGER BeforeDelete BEFORE DELETE ON Users FOR EACH ROW ...`
Pro-Tip: A "Mutating Table Error" occurs when a row-level trigger attempts to query the same table that invoked it.

Unit IV: Transaction Processing CO4

ACID & Schedules U4

Transactions guarantee Atomicity, Consistency, Isolation, and Durability. Serializability ensures concurrent execution yields results identical to some serial sequence, preventing anomalies like Dirty Reads.

Example: Using a Conflict Graph, if there's a cycle between transactions (e.g., T1 reads what T2 writes, and T2 reads what T1 writes), it is NOT conflict-serializable.
Exam Trap: View serializability is less strict than conflict serializability and accommodates blind writes (writing without reading).

Deadlock Prevention (Wait-Die vs Wound-Wait) U4

stateDiagram-v2 state Wait-Die(Non-Preemptive) { OlderTxn --> YoungerTxn : Waits YoungerTxn --> OlderTxn : Dies (Rollback) } state Wound-Wait(Preemptive) { OlderTxn2 --> YoungerTxn2 : Wounds (Preempts) YoungerTxn2 --> OlderTxn2 : Waits }

Using timestamps to prevent deadlocks: Wait-Die allows older transactions to wait for younger ones, while younger ones die. Wound-Wait preempts (wounds) the younger transaction holding the lock.

Example: In Wound-Wait, if T1 (older) requests a lock held by T2 (younger), T2 is aborted and its locks are released to T1.
Pro-Tip: A transaction that "dies" or is "wounded" retains its original timestamp upon restart, ensuring it eventually becomes the oldest and completes without starvation.

ARIES Crash Recovery U4

Utilizes Write-Ahead Logging (WAL) with Steal/No-Force buffer policies. The protocol executes three phases: Analysis, REDO (repeats history to reconstruct crash state), and UNDO (rolls back uncommitted txns).

Example: Log Sequence Numbers (LSNs) link chain records. The REDO phase re-applies logs starting from the RedoLSN found in the checkpoint.
Exam Trap: Compensation Log Records (CLRs) are written during the UNDO phase to ensure that if a crash occurs *during* recovery, UNDO operations are not repeated.

Unit V: Advanced DB & MongoDB CO5

CAP Theorem & NoSQL U5

Distributed systems can strictly guarantee only two out of Consistency, Availability, and Partition tolerance. NoSQL systems scale horizontally and typically relax Consistency (AP) or Availability (CP).

Example: MongoDB operates as a CP system by default (elects a primary, halts writes if partition causes primary loss).
Exam Trap: Network partitions (P) are unavoidable in distributed systems. Therefore, the real architectural choice is always between C and A.

MongoDB Documents & BSON U5

MongoDB eschews rigid relational schemas in favor of dynamic BSON (Binary JSON) documents. Data modeling shifts from normalization (joining tables) to embedding (storing related data inside a single document).

Example: `{ _id: 1, name: "Alice", address: { city: "NY", zip: "10001" } }`
Pro-Tip: Embed data for 1:1 or 1:few relationships to optimize read performance. Reference data for 1:Many or N:M to avoid hitting the 16MB document size limit.

Aggregation Pipeline U5

A multi-stage framework for data transformation, analogous to SQL `GROUP BY` and `JOIN`. Documents pass through stages like `$match` (filter), `$group` (aggregate), and `$project` (reshape).

Example: `db.sales.aggregate([{ $match: { status: "A" } }, { $group: { _id: "$item", total: { $sum: "$amount" } } }])`
Exam Trap: Stage order drastically impacts performance! Always place `$match` and `$sort` stages as early as possible to leverage indexes and reduce the dataset flowing into memory-intensive `$group` stages.
